# ODH Platform Utilities v2 Proposal

## Summary

Version 2 should be one Go module with one implementation of each platform
capability. The current root module and `framework/` module should be merged
under:

```text
github.com/opendatahub-io/odh-platform-utilities/v2
```

V2 requires Go 1.26. Its `go.mod` uses the Go 1.26 language level and the
repository pins a supported Go 1.26 patch release for builds and CI. This
allows option structs to use `new(value)` for explicit pointer-valued settings
without introducing pointer helper APIs. The existing v1 modules remain on
their current Go version until their code is removed or migrated.

The v2 design should separate three concerns:

1. **Domain types and primitives** — platform API types, Kubernetes helpers,
   renderers, conditions, metadata, and API discovery.
2. **Actions with two entry points** — reusable objects expose `Run` for
   programmatic use and a thin `Execute` adapter for pipeline use.
3. **Controller integration** — a reconciler and pipeline request; request
   mapping is colocated with each action rather than placed in wrapper packages.

`flakiness/` is intentionally excluded from this proposal and remains a
separate module. `framework/testing/` is not part of the public v2 library
architecture, but its harness and tests may be rewritten as needed to consume
the new APIs; preserving its current module or API shape is not a goal.

## Goals

- Merge the root and framework Go modules.
- Set Go 1.26 as the v2 minimum language version.
- Remove duplicate API, resource, condition, rendering, cache, metadata,
  deploy, and GC implementations.
- Make every retained public action useful both programmatically and in the reconciler
  pipeline.
- Colocate thin pipeline request mapping with the programmatic action while
  keeping business logic in `Run`.
- Put all public actions under one predictable package tree without parallel
  standalone/controller package hierarchies.
- Give Helm, Kustomize, and Go templates the same construction and rendering
  model.
- Keep `api` limited to the platform wire contract and accessor interfaces.
- Preserve the current `ActionError` classifiers, precedence, status, event,
  and scheduling semantics; define continuation boundaries for the new phased
  pipeline explicitly.
- Make configuration immutable after construction and invocation inputs
  explicit per `Run` call.
- Carry every current production capability into the redesign initially,
  while allowing its package, API, and implementation to be reshaped or
  consolidated. Evaluate removal only after the redesigned system makes its
  purpose, consumers, and overlap clear.

## Non-goals

- Migrating or redesigning `flakiness/`.
- Designing `framework/testing/` as a supported public v2 package or preserving
  its current API and module layout.
- Preserving v1 import paths inside the v2 module.
- Keeping both root and framework implementations behind compatibility
  aliases.
- Preserving every v1 package, exported symbol, duplicate helper, constant
  alias, or convenience API in its current shape.
- Designing a universal action result that attempts to represent every
  possible action output.
- Redesigning cross-phase `ActionError` aggregation. V2 reuses the existing
  `ActionError` accumulator, categories, precedence, and result interpretation;
  only phase-scoped continuation changes. It does not add an execution report,
  phase-result model, or second error-combination mechanism.
- Making renderer-specific concepts such as Helm values or Kustomize plugins
  part of the controller pipeline core.

The top-level layout retains the repository's `api/` and `pkg/` distinction
while removing the separate `framework/` module. Only contract types live
outside `pkg/`. The first directory below `pkg/` identifies the context:

- `pkg/platform/*` owns behavior over `api` types.
- `pkg/kube/resources/*` owns Kubernetes resource operations, including list
  access, decoding, identity, cloning, hashing, metadata transformations,
  and the shared client-backed `Apply` and `ApplyStatus` SSA operations.
- Manifest rendering is supplied directly by the `k8s-manifest-kit` renderer
  modules and engine rather than mirrored under a v2 package.
- `pkg/kube/*` owns Kubernetes-specific values, helpers, and API interaction;
  packages that perform no I/O state that boundary explicitly.
  OpenShift-specific behavior is nested below it.
- `pkg/action` owns only the domain-level `ActionError` contract and its
  semantic helpers. The controller-specific action interface belongs to
  `pkg/controller/pipeline`.
- `pkg/action/*` owns both programmatic `Run` methods and thin pipeline
  `Execute` adapters. There is no parallel `pkg/controller/action/*` tree.
- `pkg/controller/pipeline` owns action registration, guards, and execution of
  the before, main, and after phases. It is not only a collection of shared
  action types.
- `pkg/controller/reconciler` owns controller-runtime integration: object
  loading, finalizers, deletion cleanup, pipeline invocation, status apply,
  events, and conversion of the final action outcome to `ctrl.Result` and
  `error`.
- The other `pkg/controller/*` packages own focused controller integration
  capabilities. `pkg/controller` itself contains no Go files; it is only the
  directory that groups these packages.
- Do not pre-create `pkg/controller/metadata`. The shared policy contract,
  default, and composition behavior belong to `pkg/platform/metadata`.
  Controllers may implement private policies and pass them through that
  interface; introduce another public package only when a concrete reusable
  controller-specific policy exists.

This avoids broad top-level dumping-ground packages such as the current
`resources`, `utils`, and flat collections of unrelated helpers. The narrower
`pkg/kube/resources` package has one explicit scope. A package should be placed
according to the context whose vocabulary and invariants it implements, not
only according to a generic technical noun.

### Why use `kube/resources` instead of `manifest`

`Manifest` accurately describes YAML/JSON documents at the rendering boundary,
but most shared operations work on decoded Kubernetes resources. The existing
name `resources` is therefore appropriate; its v1 problem is mixed scope, not
the name itself.

V2 `pkg/kube/resources` contains reusable operations over Kubernetes resource
values together with the shared `Apply` and `ApplyStatus` SSA primitives. Its
public vocabulary can include `List`, `Accessor`, `Collection`, `Decode`, and
focused object helpers. Manifest-kit renderers return unstructured Kubernetes
resources; controller-owned rendering actions convert those values to
`resources.List` and publish them through the accessor.

GC-specific resource-type discovery lives with `pkg/action/gc`; environment
requirements live with `pkg/action/requirements`. Do not introduce a generic
discovery package until another consumer requires the same contract.
Actions use their controller-runtime client and REST mapper directly. Owner-reference
behavior remains under `pkg/kube/ownership`. Apply ordering is deploy policy and lives in
unexported code in `pkg/action/deploy/order.go`; renderers preserve engine output order.
Hashing follows the consumer rule: keep it in `pkg/kube/resources` only when
multiple genuine consumers need the same semantics; otherwise internalize it
with its action or cache.

The layout is not a relocation map. V2 retains the behavior of every current
production capability, but may combine, split, internalize, or replace its
existing implementation. Duplicate implementations, obsolete wrappers, and
unused compatibility symbols need not survive. A directory shown as
`internal` is intentionally not a consumer-facing API.

The files shown under `deploy/` illustrate the convention for every retained
action package: `action.go` contains configuration and programmatic `Run`
behavior, while `pipeline.go` contains only `Name`, `Execute`, and an optional
`Validate` implementation when that action has pipeline setup requirements.

## Dependency direction

Dependencies must flow in one direction:

```text
pkg/controller/reconciler -> pkg/controller/pipeline
pkg/controller/pipeline   -> pkg/action
pkg/action/*               -> pkg/controller/pipeline
pkg/action/*               -> pkg/action
pkg/action/*               -> pkg/platform/*, pkg/kube/*
pkg/controller/pipeline    -> api, pkg/kube/resources
pkg/platform/*             -> api
configurable pkg/*         -> pkg/option
```

An arrow means “imports.”

More precisely:

- `api` imports only Kubernetes API/runtime types required by the contract.
- `pkg/option` has no dependencies and contains only the generic `Option[T]`
  contract and function adapter.
- `pkg/action/*` may import `pkg/controller/pipeline` only for its thin
  `pipeline.go` adapter. Programmatic methods and domain implementation must
  accept action-specific run options and must not accept `pipeline.Request`.
- `pkg/action` contains only the shared action-error contract. It does not
  import `pkg/controller/pipeline` or any concrete child action package, so
  the pipeline can aggregate `action.ActionError` without an import cycle.
- `pkg/action/*` must never import `pkg/controller/reconciler`.
- `pkg/controller/pipeline` must not import concrete action packages.
- `pkg/controller/reconciler` depends on the pipeline abstraction, not on
  concrete deploy/render/GC actions.
- `pkg/kube/resources` must not import manifest renderers, `pkg/action`, or
  `pkg/controller`.
- `pkg/platform/*` may operate on `api` types but must not depend on actions or
  the controller pipeline.
- No package may import a v1 root or `framework` path.

These rules should be enforced with an architecture test rather than relying
only on review. Because Go import boundaries operate at package granularity,
the test should also inspect source files and reject references to
`pipeline.Request` outside each action package's `pipeline.go` files.

## Capability retention and package-creation rules

V2 carries all current production capability areas into the redesign:
platform API contracts, validation, conditions, metadata protocols,
Kubernetes resource manipulation, apply and status apply, discovery,
ownership, singleton handling, admission, predicates and handlers, deploy,
GC, explicit deletion, environment requirements, workload and release
observation, dynamic ownership, cache coherence, rendering, and OpenShift TLS
integration. None of
these capabilities should be removed as a prerequisite to, or assumption of,
the redesign.

Once the redesigned packages, contracts, and lifecycle are concrete, each
capability can be evaluated with better evidence. A later decision may remove
a capability that has no remaining use, is fully superseded upstream, or is
made unnecessary by the new architecture. That is a post-redesign review, not
part of defining the initial v2 shape.

Initial capability retention does not mean exported-symbol or package parity
with v1. A capability may be provided by a consolidated implementation, an
internal package owned by its only consumer, or a direct upstream dependency.
Duplicate implementations, forwarding wrappers, suffix-only constants, and
aliases may be consolidated while redesigning because this changes their
representation rather than prejudging whether the underlying capability is
needed.

Before removing or renaming a public v1 symbol, migration work must still check
known module-controller imports in addition to repository-local references.
That audit determines the migration guide and replacement path; it does not
decide whether the underlying capability belongs in v2.

Create a public package only when it owns a coherent vocabulary or behavior.
In particular:

- do not create a package solely to preserve old import paths;
- do not create packages for suffix constants, one-line forwarding helpers,
  or wrappers that add no invariant;
- prefer an `internal` package when only one action or context consumes the
  behavior;
- prefer the upstream controller-runtime or Kubernetes API when the current
  helper only renames it; and
- keep related constants together only when they form a documented protocol.

### Concrete consolidation decisions

- Remove `framework/metadata`. Its suffix constants are implementation
  fragments, not an independent API. Retained full metadata keys belong to
  `pkg/platform/metadata/labels` or
  `pkg/platform/metadata/annotations`.
- Preserve the metadata protocols used by the platform contract,
  deploy/GC/ownership, handlers, and predicates. Canonicalize their full keys;
  unused aliases and prefixes do not need separate exported identities in v2.
- Retain the label and annotation subpackages because the default deploy/GC
  policy is a shared protocol. Keep only the keys used by that protocol or by
  another verified platform contract; colocate incidental action-only keys
  with their action.
- Keep label-value normalization with `pkg/platform/metadata/labels` only
  because deploy, GC, and ownership must normalize identically. Coordinate
  deploy stamping and GC selection through the shared
  `pkg/platform/metadata.Policy`.
- Move `EnqueueByOwnerAnnotation` to `pkg/controller/handler`; it is event
  routing, not Kubernetes discovery or ownership mutation. Although it is
  configured alongside watch predicates, its result is a controller-runtime
  `handler.MapFunc`, so it belongs with handlers.
- Keep `pkg/controller/predicate` as one cohesive public package rather than
  preserving nested packages for each predicate family. Audit every predicate
  against controller-runtime: rework unclear names, remove redundant
  wrappers, and retain only predicates with a real v2 use case.
- Keep owner-reference construction in `pkg/kube/ownership`. Keep generic
  label, annotation, and namespace mutation in `pkg/kube/resources` only if
  the v2 renderer/action APIs actually use it.
- Keep RBAC rule evaluation as unexported code in `pkg/action/gc/rbac.go` while
  GC remains its only production consumer.
- Internalize action caches and metrics with their owners. Do not retain
  generic `pkg/cache` or `pkg/metrics` packages without independent consumers.
- Remove the framework manager wrapper. Renderer source paths become explicit
  renderer requests, and the cache-coherent client wrapper is private
  controller plumbing if it remains necessary.
- Reshape current precondition checks as ordinary framework actions registered
  in the before phase. Preserve the existing check capabilities through these
  actions rather than through a special precondition framework.
- Keep a small public `pkg/kube/gvk` package for generic, reusable GVKs such
  as `Deployment` and `ServiceAccount`, which are useful when configuring
  requirements, discovery, and action policies. Do not turn it into a catalog
  of distribution-specific or consumer-local CRDs; those remain with their
  consumers.
- Merge template helper functions into the template renderer rather than
  retaining a generic `utils/template` package.
- Exclude framework test matchers along with `framework/testing` from this
  proposal; they require a separate consumer and support decision.

## API package: types only

The v2 `api` package should contain:

- platform wire types;
- JSON/YAML tags and kubebuilder validation/list markers;
- typed constants such as condition types, phases, and management states; and
- stable cross-context value types that consumers exchange independently of
  an implementation; and
- accessor interface declarations used by generic controller code.

It should not contain:

- constructors;
- validation functions;
- condition CRUD or aggregation;
- release lookup/upsert helpers;
- status persistence;
- rendering or resource helpers; or
- domain methods such as `Status.GetConditions`,
  `ReleaseStatus.SetRelease`, or `GetPlatformRelease`.

Those behaviors move to `pkg/platform/condition`, `pkg/platform/release`,
`pkg/platform/validation`, and `pkg/kube/resources`.

Platform information is a typed snapshot of the running software and the
environment in which it runs:

```go
package api

type PlatformKind string
type DistributionKind string

type Distribution struct {
    Kind    DistributionKind `json:"kind"`
    Version string           `json:"version,omitempty"`
}

type PlatformProfile struct {
    Kind         PlatformKind      `json:"kind"`
    Version      string            `json:"version,omitempty"`
    Distribution Distribution      `json:"distribution"`
    Annotations  map[string]string `json:"annotations,omitempty"`
}
```

`Kind`, `Version`, and the nested distribution kind/version are common,
portable fields. They are open string types rather than closed enums so a new
product or Kubernetes distribution does not require a schema change.
`Annotations` carries additional distribution-owned facts using qualified key
names; unknown annotations are preserved and ignored. These annotations are
profile data and are never copied automatically onto managed Kubernetes
resources.

The distribution integration owns how the profile is populated. It may inspect
environment variables, OLM resources, OpenShift APIs, or other
distribution-specific sources, but none of those mechanisms shape the shared
API. The shared library provides no universal platform detector, no built-in
precedence among sources, and no assumption that a missing value implies a
default platform.

Consequently, the current `Platform`, `ClusterType`, `ClusterInfo`,
`AuthenticationMode`, and `OperatorInfo` types do not move into v2 `api`.
Distribution-specific code may keep private equivalents with its detector, or
remove them when a direct result is sufficient. Actions should prefer generic
API/GVK capability discovery over branching on a cluster distribution. A
public Kubernetes discovery result type should be retained under `pkg/kube`
only when the v2 consumer audit demonstrates an independent portable use case.

The profile is computed once during process bootstrap and then treated as an
immutable value. Bootstrap code passes it explicitly to ordinary functions and
to action or policy constructors that need it. Components retaining it must
clone `Annotations`; there is no package-global current profile. The profile is
not added to `pipeline.Request` and is never rediscovered per reconciliation.

`PlatformProfile` is observed information and must never appear in a shared
spec type or control desired-state rendering by being read back from status. A
module may project the immutable startup value into its status through the
optional accessor defined below. Missing or stale status therefore cannot
change reconciliation behavior. Lookup, merge, detection, and defaulting
behavior does not belong in `api`.

A reduced contract is preferable:

```go
package api

type Status struct {
    ObservedGeneration int64       `json:"observedGeneration,omitempty"`
    Conditions         []Condition `json:"conditions,omitempty"`
}

type ReleaseStatus struct {
    Releases []ComponentRelease `json:"releases,omitempty"`
}

type PhaseStatus struct {
    Phase Phase `json:"phase,omitempty"`
}

type StatusAccessor interface {
    GetStatus() *Status
}

type ConditionsAccessor interface {
    GetConditions() []Condition
    SetConditions([]Condition)
}

type ReleaseStatusAccessor interface {
    GetReleaseStatus() *ReleaseStatus
    SetReleaseStatus(ReleaseStatus)
}

// PhaseStatusAccessor is an opt-in capability. It is intentionally not part of
// PlatformObject.
type PhaseStatusAccessor interface {
    GetPhaseStatus() *PhaseStatus
    SetPhaseStatus(PhaseStatus)
}

// PlatformProfileAccessor opts an object into status projection of the
// immutable startup profile. It is intentionally not part of PlatformObject.
type PlatformProfileAccessor interface {
    GetPlatformProfile() *PlatformProfile
    SetPlatformProfile(PlatformProfile)
}

type PlatformObject interface {
    client.Object
    StatusAccessor
    ReleaseStatusAccessor
}
```

`PlatformObject` requires only the common status and release-status accessors.
`ConditionsAccessor`, `PhaseStatusAccessor`, and `PlatformProfileAccessor` are
separate opt-in capabilities. Condition helpers operate on
`ConditionsAccessor` rather than depending on concrete status layout or a
pipeline manager. Declaring these interfaces in `api` is type-only; the API
status structs do not need behavioral methods.

`api.Status` is deliberately limited to the fields common to every platform
object: observed generation and conditions. Release status is a separate API
wire type and a required `PlatformObject` capability through
`ReleaseStatusAccessor`; it must not be nested into `api.Status`. Release
helpers operate on
`ReleaseStatusAccessor` or its returned `*api.ReleaseStatus`.

These fragments are composed by a concrete module status rather than nested in
the common type:

```go
type MyModuleStatus struct {
    api.Status        `json:",inline"`
    api.ReleaseStatus `json:",inline"`
    api.PhaseStatus   `json:",inline"` // optional
    Platform          *api.PlatformProfile `json:"platform,omitempty"` // optional
}
```

Conditions and phase are opt-in behavior even though `Condition` and
`PhaseStatus` remain API wire types. Objects that expose condition operations
implement `ConditionsAccessor`; objects that expose phase storage implement
`PhaseStatusAccessor`. Reconciler status processing detects each interface with a
type assertion and only performs the corresponding work when the object opts
in.

When the reconciler is configured with the startup profile and the object
implements `PlatformProfileAccessor`, status processing copies that immutable
value into the status field before persistence. The reconciler never reads
the profile back from status.

`validation.Validate` should detect nil or copy-returning status and release
accessors. It should validate condition and phase round-tripping only when the
object implements `ConditionsAccessor` or `PhaseStatusAccessor`, respectively,
and profile round-tripping when it implements `PlatformProfileAccessor`.

### Generated DeepCopy methods

Generated `DeepCopy` and `DeepCopyInto` methods are safe and explicitly
allowed. They are mechanical support for Kubernetes API types, not API-domain
logic.

The boundary is strict: `api` may contain type declarations, constants,
accessor interfaces, schema markers, and generated deep-copy code. It must not
contain any other exported functions or behavioral methods.

The generated file must remain clearly marked. A compile fixture should
generate a module CR that embeds the v2 status/release types and verify that
its generated deepcopy is correct.

## Action model

Every public concrete action should be a reusable struct. Actions that participate in
the resource flow accept `resources.Accessor`, not a pipeline
request or a concrete pipeline-owned list:

```go
action := deploy.New(
    deploy.WithCache(&deploy.CacheOptions{TTL: 10 * time.Minute}),
)

resourceSet := resources.New(objects)
result, err := action.Run(ctx, &deploy.RunOptions{
    Client:    kubeClient,
    Owner:     component,
    Resources: resourceSet,
})
```

The same value is directly registrable in the pipeline:

```go
reconciler.WithAction(action)
```

The constructor holds stable policy. `Run` receives values that vary per
invocation, while `Execute` maps `pipeline.Request` into those same run inputs.
All action constructors are error-free and provide sensible behavioral
defaults for optional behavior. Required dependencies have no meaningful safe
default and are positional constructor arguments; functional options configure
only optional policy. This makes omission a compile-time error while preserving
an error-free constructor. GC type discovery is the explicit case in this
proposal.

### Resource access

The resource accessor is shared library behavior under `pkg`, not part of the
platform API contract:

```go
package resources

type List []client.Object

type Predicate func(client.Object) bool

type TransformFunc func(
    index int,
    object client.Object,
) (client.Object, error)

type Accessor interface {
    All() iter.Seq2[int, client.Object]

    Get() List
    Set(List)
    SetAt(index int, object client.Object) error
    Append(objects ...client.Object)
    Filter(Predicate) int
    Transform(TransformFunc) error
}

type Collection struct {
    // unexported storage
}

func New(initial List) *Collection
```

`resources.Collection` is the default implementation for programmatic use.
`pipeline.Request` carries the same interface as an explicit field. The
action's `Execute` method passes the field to `Run` without adapting or copying
it:

```go
deployAction.Run(ctx, &deploy.RunOptions{
    Resources: req.Resources,
})
```

Prefer this composition over making `pipeline.Request` implement the
interface. A reconciliation request is a container of invocation context, not
itself a resource collection. The field also makes resource access visible in
the action mapping and permits a focused test implementation when needed.

The accessor uses explicit write-back and copy-on-write semantics without
deep-copying the complete resource graph at every boundary:

- `All` is a zero-allocation lazy iterator over the current collection and
  yields the index and a borrowed, read-only object. `SetAt` may replace the
  current object during iteration because it does not change collection
  structure. `Set`, `Append`, `Filter`, and `Transform` must not be called until
  that iteration ends.
- `Get` returns a shallow copy of the slice. Its objects are borrowed and must
  be treated as read-only.
- `Set` replaces the complete collection and shallow-copies the slice
  structure. `SetAt` bounds-checks and replaces one object. `Append`, `Set`,
  and `SetAt` take ownership of the supplied object references; callers must
  not mutate those objects afterward.
- `Filter` retains objects for which its predicate returns `true`, updates the
  collection in place, and returns the number discarded. Its predicate receives
  borrowed, read-only objects.
- `Transform` shallow-clones the slice, invokes the callback in index order,
  and publishes the replacement slice only after every callback succeeds. The
  callback treats its input as read-only and returns either the same object for
  no change or a caller-created deep copy for replacement. A callback error
  leaves the collection unchanged.

This collection `TransformFunc` is not a rendering extension point. Rendering
filters and transformers use the contracts supplied directly by manifest-kit.

The current request-specific `AddResources`, `ForEachResource`, and
`RemoveResources` behavior moves to `Append`, `All`/`Transform`, and `Filter`,
respectively; migrating a removal predicate requires negating it because
`Filter` uses retain semantics. Typed-object-to-unstructured conversion remains
a separate conversion helper rather than hidden accessor behavior.

`Accessor` is an ordered storage abstraction, not an identity index or
validation boundary. It preserves insertion order and duplicate entries and
does not resolve GVKs, default namespaces, deduplicate identities, or silently
discard nil or incomplete objects. It therefore needs neither a Kubernetes
client nor a scheme. Actions validate the requirements of the operation they
perform.

Deploy is the authoritative desired-resource validation boundary. Before any
API write, it resolves typed-object GVKs through its scheme, applies namespace
defaulting where appropriate, rejects nil objects and missing required identity
fields, and rejects duplicate `(GVK, namespace, name)` identities. It then
publishes the normalized, metadata-decorated collection back through the
accessor so later deploy-adjacent actions and GC observe exactly the identity
set used for apply. Renderers may return unnormalized typed or unstructured
objects and remain independent of a Kubernetes scheme.

Do not place `resources.Accessor` in `api`: rendered resources are transient
reconciliation state, not part of the platform wire contract. Do not make the
interface depend on `pipeline.Request`, and do not add controller-specific
operations to it. Conversion from typed objects, rendering, ordering, and
deployment remain responsibilities of their respective packages.

### Configuration option pattern

Use the controller-runtime option style with the small generic core demonstrated
by [k8s-manifest-kit](https://github.com/k8s-manifest-kit/pkg/blob/main/util/option.go):
one generic option interface, one function adapter, and an exported full options
struct for every option family.

```go
package option

type Option[T any] interface {
    ApplyTo(*T)
}

type FunctionalOption[T any] func(*T)

func (f FunctionalOption[T]) ApplyTo(target *T) {
    f(target)
}
```

Keep this dependency-free primitive under `pkg/option`. Public packages alias
it for their own configuration type, so callers normally use only the owning
package. Every first-party functional-option family must also have a complete
struct form; do not expose a function-only option family.

```go
package deploy

type Mode uint8

const (
    ModeUnspecified Mode = iota
    ModeSSA
    ModePatch
)

type Options struct {
    Mode                 Mode
    MetadataPolicy       platformmetadata.Policy
    FieldOwner           string
    CRDFieldOwner        string
    Labels               map[string]string
    Annotations          map[string]string
    Sort                 SortFunc
    Cache                *CacheOptions
    MergeStrategies      map[schema.GroupVersionKind]MergeFunc
    ExcludeFromOwnership []schema.GroupVersionKind
    ContinueOnError      bool
}

func (o Options) ApplyTo(target *Options) {
    // Merge each field according to its documented semantics.
    // Clone maps, slices, and pointers; never retain caller-owned storage.
}

type Option = option.Option[Options]

func WithMode(mode Mode) Option {
    return option.FunctionalOption[Options](func(opts *Options) {
        opts.Mode = mode
    })
}
```

This allows both forms:

```go
deploy.New(
    deploy.Options{Mode: deploy.ModeSSA},
    deploy.WithLabel("app.kubernetes.io/name", "my-module"),
)
```

Every constructor/configuration option family defines one authoritative set of
safe defaults. `New` creates the effective `Options` value with those defaults
and then applies every supplied option from left to right:

```go
func New(opts ...Option) *Action {
    effective := Options{
        Mode:           ModeSSA,
        MetadataPolicy: platformmetadata.DefaultPolicy(),
        Sort:           defaultApplyOrder,
        // Remaining sensible defaults.
    }

    for _, opt := range opts {
        opt.ApplyTo(&effective)
    }

    return newAction(effective)
}
```

The same initialization rule applies at the corresponding boundary for
non-constructor families: `Run` initializes optional invocation defaults,
action registration initializes `ActionOptions`, and condition marking
initializes `MarkOptions` before applying their options.

The exported struct is applied over the options initialized by the owning entry
point. Zero and nil semantics are defined per field rather than by one generic
presence rule. For example:

- an unspecified enum value may retain the initialized default;
- a false boolean may mean disabled or may retain a default, according to the
  named behavior;
- a zero duration may disable a timeout while a positive duration replaces
  it; and
- a nil collection may retain a default while a non-nil empty collection
  explicitly clears it.

Each field documents its own rule, and its `WithX` function follows exactly the
same rule. Later options win for fields they actually apply. Collection and
nested-option merge behavior follows the patterns used by
[manifest-kit engine options](https://github.com/k8s-manifest-kit/engine/blob/main/pkg/engine_option.go)
and
[Helm renderer options](https://github.com/k8s-manifest-kit/renderer-helm/blob/main/pkg/helm_option.go):

- append ordered slices when each option contributes another pipeline element;
- replace slices or maps when the field represents one complete configured set;
- clone replacements so the constructed object does not alias caller storage;
- apply nested options recursively instead of replacing an already initialized
  nested configuration; and
- replace scalar values only when the field's presence rule says the source is
  set.

Avoid pointers as the default way to represent every scalar. Plain values are
appropriate when their zero value unambiguously means either the default or an
active setting. Use an enum with an `Unspecified` value when named states make
the API clearer. A pointer is required when merging must distinguish omission
from an explicit zero value. Because v2 requires Go 1.26, use `new(value)` for
that exceptional struct form rather than adding a pointer helper:

```go
reconciler.Options{
    CleanupTimeout: new(time.Duration(0)), // explicitly disabled
}
```

An option struct's `ApplyTo` clones a present pointer value before assigning it
to the target. Functional options should construct and apply the same presence
state rather than maintaining separate semantics.

After all options have been applied, `New` stores a cloned, fully resolved
configuration in the action. Actions do not retain caller-owned mutable values
or repeatedly reinterpret defaults during `Run`.

The rule applies consistently across the proposal:

| Functional-option family | Complete struct option |
| --- | --- |
| action construction, such as `deploy.Option` or `gc.Option` | package-local `Options` |
| action invocation, such as `deploy.RunOption` | package-local `RunOptions` |
| pipeline registration, `pipeline.ActionOption` | `pipeline.ActionOptions` |
| pipeline construction, `pipeline.Option` | `pipeline.Options` |
| reconciler construction, `reconciler.Option` | `reconciler.Options` |
| condition marking, `condition.MarkOption` | `condition.MarkOptions` |
| dynamic discovery, `gc.DynamicDiscoveryOption` | `gc.DynamicDiscoveryOptions` |

Each struct implements its associated option interface and can be mixed with
functional options in one left-to-right list. Fluent topology methods such as
`WithAction` and fluent domain methods such as `ActionError.WithRequeueAfter`
are not functional options and do not create artificial option structs.
Options owned by manifest-kit remain governed by their upstream API.

#### Option file naming

All declarations belonging to one first-party option family live together in a
file whose name ends in `*_options.go`. That file contains:

- the exported complete options struct;
- its `ApplyTo` implementation;
- the package-local alias of `option.Option[T]`;
- all related `WithX` functional options; and
- the default-options function when the family has defaults.

Use the family or configured component as the prefix. Examples include
`deploy_options.go`, `run_options.go`, `action_options.go`,
`mark_options.go`, `dynamic_discovery_options.go`, and
`reconciler_options.go`. Packages with multiple option families use one file
per family rather than combining unrelated options into a generic
`options.go`. Related tests use the matching `*_options_test.go` name.

The shared generic definitions are the deliberate exception and remain in
`pkg/option/option.go`. A file must not be named literally `_options.go`:
the Go tool ignores source files whose names begin with `_`; `_options.go` is
the required suffix, not the complete filename.

Rules:

- Apply options from left to right; later options win for scalar/map keys.
- Every functional option writes a field represented by its family's exported
  options struct; the struct can configure the same behavior without calling
  the function.
- A non-nil collection in an options struct replaces the corresponding
  default; individual `WithX` options append or merge as their name implies.
- Document zero and nil semantics for every option field; do not impose one
  package-wide meaning on all scalar, interface, and collection values.
- Prefer documented zero semantics, directed field names, and small mode enums
  when omission and zero do not need to differ. Use a pointer when that
  distinction is required, and use Go 1.26's `new(value)` to construct it.
- For every slice, map, and nested options field, document whether applying it
  appends, replaces, merges by key, or recursively applies.
- Clone mutable values and present pointer values while applying options.
- Define one authoritative default set per option family. The owning entry
  point initializes that set before applying struct or functional options.
- Document and test the zero-option behavior of every action. An omitted option
  must never leave an ambiguous mode, nil strategy, unbounded selector, or
  disabled safety check.
- Do not allow options to mutate the constructed action after `New` returns.
- Action constructors are total and return `*Action`, never `(*Action, error)`.
- Design options as valid transformations over a complete default. Required
  dependencies are positional constructor arguments; optional nil values leave
  the current/default value unchanged rather than creating a broken action.
- `Validate() error` is an optional pipeline capability, not part of the
  minimum action contract. An action implements it only when it has static
  setup requirements that the reconciler can check during `Build`.
- Programmatic `Run` independently validates its action-specific run inputs
  and stable configuration before any I/O. It must not rely on pipeline
  validation having happened.
- Parsing, filesystem access, discovery, and other fallible runtime work do not
  belong in action constructors. Non-action constructors, such as renderer or
  source constructors, may still return errors when validation is intrinsic to
  creating that value.

### Per-run option pattern

Per-invocation inputs use the same style:

```go
type RunOptions struct {
    Client    client.Client
    Owner     client.Object
    Resources resources.Accessor
}

func (o RunOptions) ApplyTo(target *RunOptions) {
    // Copy explicitly supplied invocation values.
}

type RunOption = option.Option[RunOptions]

func (a *Action) Run(ctx context.Context, opts ...RunOption) (Result, error)
```

The full `RunOptions` struct is the preferred form when several required
inputs must be supplied together. Small functional run options remain useful
for `Execute` implementations and tests. `Run` must validate required values
before doing I/O. `RunOptions` defaults only genuinely optional invocation
values; unlike constructor `Options`, its zero value cannot make required
inputs such as the client, owner, or resource accessor optional.

Required constructor arguments should remain positional when they are truly
stable dependencies shared by every invocation. For actions whose Kubernetes
client comes from the reconciliation request, the client belongs in
`RunOptions`, allowing one action instance to remain independent of a manager.

The client type in the example is illustrative rather than universal. Each
action must select the narrowest existing controller-runtime client interface
that supports its complete behavior:

- `client.Reader` for actions that only call `Get` or `List`;
- `client.Writer` for actions that only mutate resources; or
- `client.Client` when the action genuinely combines reads and writes or needs
  the scheme, REST mapper, status, or subresource facilities exposed by the
  complete client.

Do not define project-specific client interfaces or mechanically use
`client.Client` for every action. In particular, deploy uses `client.Client`
because its merge and apply behavior reads existing resources, performs
writes, and resolves object types. GC also uses `client.Client` because it
lists candidates, creates authorization review resources, deletes stale
objects, and needs REST mapping. Read-only checks use `client.Reader`, while a
pure deletion action can use `client.Writer`.

`pipeline.Request.Client` remains `client.Client` as the framework's shared
client source. Go's structural interface satisfaction lets an `Execute`
adapter pass it directly into an action's narrower `client.Reader` or
`client.Writer` run option. No wrapper or type assertion is required.

### Results

Do not create one universal result type. Each action should return the smallest
domain result its caller needs. Desired resources themselves flow through
`resources.Accessor`; results report outcomes rather than duplicating
that shared state:

- deploy: applied/skipped resource identities or counts;
- GC: examined/deleted counts;
- status checks: an `api.Condition` or typed observation;
- delete/sanity check: error only unless counts are useful.

Returning useful results avoids forcing programmatic callers to pass pointers
solely so actions can communicate outputs.

## Pipeline action model

The pipeline should use a small, controller-specific contract:

```go
package pipeline

type Action interface {
    Name() string
    Execute(context.Context, *Request) error
}

type Validator interface {
    Validate() error
}

type ActionFunc struct {
    ActionName string
    ExecuteFunc func(context.Context, *Request) error
}

func Wrap(execute func(context.Context, *Request) error) Action

type Registration struct {
    // private action, name, and guard state
}

func Register(action Action, opts ...ActionOption) Registration

type Options struct {
    Before  []Registration
    Main    []Registration
    After   []Registration
    Cleanup []Registration
}

func (o Options) ApplyTo(target *Options)

type Option = option.Option[Options]

func New(opts ...Option) *Pipeline

type Pipeline struct {
    // private immutable registration snapshots
}

func (p *Pipeline) Validate() error

func (p *Pipeline) Run(
    context.Context,
    *Request,
) action.ActionError

func (p *Pipeline) Cleanup(
    context.Context,
    *Request,
) action.ActionError
```

Using a named interface improves logs and metrics. `ActionFunc` keeps custom
one-off actions convenient, while `Wrap` is the short form for adapting a
function or controller method:

```go
pipeline.Wrap(controller.renderResources)
```

`Wrap` derives a default name once, when the wrapper is constructed, from the
function's runtime symbol. Named functions and methods therefore do not require
an explicit name. Anonymous functions and closures receive their compiler-
generated symbol; callers may use `pipeline.WithName` when a more readable name
or a collision-free name is needed. The effective name must still be non-empty
and unique when `Build` validates the pipeline. Name derivation happens during
setup, never during reconciliation. Both forms intentionally implement only
the minimum `Action` contract. A custom action with static setup requirements
can additionally implement `Validator`.

`WithBeforeAction`, `WithAction`, `WithAfterAction`, and
`WithCleanupAction` accept `Action`. The action's `Name()` is its default
registration name; callers override that identity only when needed with
`pipeline.WithName`. Each builder method delegates to `pipeline.Register` and
stores the resulting registration in its corresponding phase. During
`Pipeline.Validate`, the pipeline uses a type assertion and calls `Validate`
only when the registered action implements `Validator`:

```go
if validator, ok := registered.Action.(pipeline.Validator); ok {
    if err := validator.Validate(); err != nil {
        return fmt.Errorf(
            "validating %s action %q: %w",
            registered.Phase,
            registered.Name,
            err,
        )
    }
}
```

The builder may also provide function conveniences that call `pipeline.Wrap`
internally. They keep the common controller-method case concise while using
the same registration options for names, guards, validation, and execution:

```go
func (b *Builder) WithBeforeActionFunc(
    execute func(context.Context, *pipeline.Request) error,
    opts ...pipeline.ActionOption,
) *Builder

func (b *Builder) WithActionFunc(
    execute func(context.Context, *pipeline.Request) error,
    opts ...pipeline.ActionOption,
) *Builder

func (b *Builder) WithAfterActionFunc(
    execute func(context.Context, *pipeline.Request) error,
    opts ...pipeline.ActionOption,
) *Builder

func (b *Builder) WithCleanupActionFunc(
    execute func(context.Context, *pipeline.Request) error,
    opts ...pipeline.ActionOption,
) *Builder
```

Each method is equivalent to passing `pipeline.Wrap(execute)` to its
corresponding action method. The function name is normally sufficient:

```go
builder.WithActionFunc(controller.renderResources)
```

Use `pipeline.WithName` only when overriding the derived name is useful:

```go
builder.WithActionFunc(
    controller.renderResources,
    pipeline.WithName("render-component-manifests"),
)
```

`WithActionFunc` is the descriptive name for this API; an abbreviated
`WithActionW` would obscure that it wraps a function and would be inconsistent
with the phase-specific helpers.

The same rule applies to before, main, after, and cleanup actions. This
preserves fluent, error-free action construction while allowing actions with
meaningful static constraints to fail before the controller starts. Actions
whose defaults form a complete pipeline configuration need no `Validate`
method.

`pipeline.New` takes one complete `pipeline.Options` value, copies all phase
registrations, and returns an immutable `Pipeline`. The reconciler constructs
that value once during `Build`, adds framework-owned registrations such as
dynamic ownership before construction, and calls `p.Validate()` exactly once.
The pipeline owns all four phase collections, but `Run` executes only before,
main, and after actions. `Cleanup` executes only cleanup actions. Neither
method accepts a phase selector, so normal reconciliation cannot accidentally
enter deletion cleanup or vice versa.

The different method name is intentional: Go cannot overload the
action-specific `Run` method with a pipeline request signature. A concrete
action can therefore implement both APIs without an adapter type or package:

```go
func (a *Action) Run(ctx context.Context, opts ...RunOption) (Result, error)
func (a *Action) Execute(ctx context.Context, req *pipeline.Request) error
```

`Execute` contains mapping only and calls `Run`; it never contains domain
logic. An action may be usable programmatically while still requiring
pipeline-only binding configuration. In that case `Run` remains valid, and the
action implements `Validator` so pipeline registration fails during `Build`
until the binding is supplied.

`pipeline.Request` should contain only invocation state shared by ordinary
actions. It must not expose the reconciler or controller as a service locator:

```go
type Extension map[string]any

type Request struct {
    Client     client.Client
    Instance   api.PlatformObject
    Resources  resources.Accessor
    Extensions Extension
}
```

The reconciler initializes `Extensions` to an empty `Extension` map for every
request. Keys must be namespace-qualified strings. The pipeline is sequential,
so extensions do not add synchronization, accessors, generic keys, or a
concurrent-map abstraction.

Controller topology and framework-maintained state—including dynamic watch
registration, registered GVKs, discovery clients, and condition
aggregation—do not belong in `Request`. A focused action receives dependencies
through constructor or run options. A dynamic type discoverer captures its
discovery client during construction. Framework-only work that is part of
action execution, such as dynamic-watch synchronization, captures reconciler
state in private actions installed by the reconciler; status computation and
persistence remain post-pipeline status processing.

The complete client in `Request` is framework wiring, not the mandatory client
type for action run options. Each `Execute` method passes it as the smallest
applicable standard controller-runtime interface selected by the action:
`client.Reader`, `client.Writer`, or `client.Client`.

The reconciler initializes `Resources` with `resources.New(nil)` when
constructing the request. A supplied accessor is preserved, which keeps tests
and custom pipeline assembly straightforward. Pipeline setup and programmatic
`Run` methods must reject a missing accessor before doing I/O. The field
exposes resource capability, not the mutable `resources.List` storage itself.

`Release` should not be part of `Request`, and deploy and GC should not depend
on it directly. Their actual shared concern is managed-resource membership,
not platform-release semantics. That membership has a default; GC's independent
type-discovery dependency is created during controller setup:

```go
reconciler.WithAction(deploy.New())
reconciler.WithAction(gc.New(typeDiscovery))
```

Both actions receive the owner and client in their run options and use the same
metadata-policy contract:

```go
package metadata

type Policy interface {
    Apply(
        scheme *runtime.Scheme,
        owner client.Object,
        object metav1.Object,
    ) error

    Matches(
        scheme *runtime.Scheme,
        owner client.Object,
        object metav1.Object,
    ) (bool, error)

    Selector(
        scheme *runtime.Scheme,
        owner client.Object,
    ) (labels.Selector, error)
}

func Compose(first Policy, additional ...Policy) Policy
```

Use the standard `metav1.Object` interface for target objects. It is the
metadata-only surface needed here, and both `client.Object` and
`*unstructured.Unstructured` already implement it. Do not introduce another
metadata accessor, require a full `client.Object`, or expose a concrete
`metav1.ObjectMeta` value that could imply ownership of names, UIDs,
finalizers, or managed fields.

Deploy calls `Apply` for each desired object. GC calls `Selector` only to
narrow API listing, requires an actual Kubernetes owner reference to the
reconciled object, and then may call `Matches` to evaluate whether the
candidate carries the metadata produced by the current policy. `Apply` may
mutate only labels and annotations.

`Selector` and `Matches` are classification and efficiency mechanisms, not
ownership. A matching label or annotation never authorizes deletion. GC must
confirm the candidate's owner reference, including the owner's UID, before any
metadata mismatch or desired-set difference can make the object deletable.

The GC candidate loop is therefore ordered as follows:

```text
list objects using Policy.Selector(owner)
-> owner reference absent: skip
-> controller owner reference does not match owner UID: skip
-> managed-resource opt-out present: skip
-> evaluate desired identity and Policy.Matches
-> delete only an owned stale object
```

The owner check uses Kubernetes controller ownership semantics—for example,
`metav1.IsControlledBy(candidate, owner)`—rather than reconstructing ownership
from metadata. An object without a matching controller owner reference is
outside generic GC even when every policy label and annotation matches. A
resource intentionally excluded from owner references must use an explicit,
separately configured cleanup mechanism; generic GC does not claim it through
metadata.

The metadata package provides `DefaultPolicy() Policy`. It consolidates the
useful owner-derived metadata already applied by today's deploy and ownership
utilities, using only the supplied owner:

- label `platform.opendatahub.io/part-of=<normalized owner kind>`;
- annotation `platform.opendatahub.io/instance.name=<owner name>`;
- annotation `platform.opendatahub.io/instance.namespace=<owner namespace>`;
- annotation `platform.opendatahub.io/instance.uid=<owner UID>`; and
- annotation `platform.opendatahub.io/instance.generation=<owner generation>`.

`Apply` stamps this complete set. `Selector` uses only the stable `part-of`
label because Kubernetes cannot select annotations. `Matches` checks the full
owner-derived metadata, including generation, but only after GC has established
ownership from the Kubernetes owner reference. After a complete successful
deploy, every desired object matches; an older generation identifies an owned
object not deployed during the current owner generation. `DefaultPolicy`
requires a resolvable owner kind, name, and UID; the namespace may be empty for
a cluster-scoped owner.

Both `deploy.New()` and a configured `gc.New(...)` install this policy before applying options.
Omitting `WithMetadataPolicy` therefore gives programmatic callers coordinated
deploy and collection behavior without framework setup. The default must be
applied uniformly to CRDs and ordinary resources; do not retain the current
CRD-specific `part-of=platform` fallback or omit owner annotations from CRDs.

Deploy applies the policy to its desired snapshot and publishes the decorated
snapshot through `resources.Accessor`. Downstream actions, including
GC, consequently observe the same metadata that deploy sent to the API rather
than a second reconstruction of it.

Policies are composable. `metadata.Compose` returns a `Policy` with these
semantics:

- `Apply` invokes every policy in registration order;
- `Selector` is the logical intersection of every policy selector; and
- `Matches` is true only when every policy matches.

A policy that contributes annotations but no discovery constraint returns
`labels.Everything()` from `Selector`, which is the neutral element in the
intersection. A caller-owned release/profile policy therefore cannot
accidentally narrow GC discovery by release.

The required first argument makes an accidentally empty composition
unrepresentable. `Compose` copies the supplied policy slice and the constituent
policies must be immutable. After applying the policies, the composite verifies
that the final metadata satisfies every constituent policy; conflicting
policies fail the action instead of producing metadata that GC cannot select.

Both actions expose `WithMetadataPolicy(metadata.Policy)` for replacing the
default. An aggregate remains one `Policy`, so deploy and GC do not need a
second multi-policy option API. The same immutable composite should be passed
to both actions. A distribution integration may provide a focused policy based
on its immutable startup profile and release information; bootstrap code
composes that policy with the platform default:

```go
metadataPolicy := platformmetadata.Compose(
    platformmetadata.DefaultPolicy(),
    distributionMetadataPolicy,
)

reconciler.
    WithAction(deploy.New(
        deploy.WithMetadataPolicy(metadataPolicy),
    )).
    WithAction(gc.New(
        typeDiscovery,
        gc.WithMetadataPolicy(metadataPolicy),
    ))
```

Profile and release values cannot be derived from `client.Object`, so they are
intentionally absent from `DefaultPolicy` and are not deploy or GC options. The
shared library does not define distribution-specific profile keys or a
universal release/profile policy. A caller-owned policy may project selected
profile or release values in `Apply` and compare them in `Matches`, but must not
add release values to `Selector`. Old-release resources therefore remain
visible to GC and can be classified as stale. Composition is bootstrap's
responsibility.

`deploy.WithLabels` and `deploy.WithAnnotations` still add ordinary metadata
independently of the policy. Deploy applies those values first and the policy
second, so generic options cannot override keys reserved by the active policy.
There should be no separate `gc.WithSelector` that can drift from deploy:
custom metadata selection belongs in a `metadata.Policy`. Constructors clone
all supplied maps and retain only immutable policy instances.

Policy selectors only narrow candidate discovery; they do not define the
population GC is authorized to delete. The GC action accepts the same
`resources.Accessor` used by render and deploy, indexes desired objects by GVK,
namespace, and name, and considers only candidates controlled by the supplied
owner. Objects with no matching controller owner reference are skipped. GC
continues to honor unremovable GVKs and the managed-resource opt-out
annotation.

This desired-set comparison replaces the current generation/type/version
annotation heuristic. Consequently, GC never requires those values. Do not put
a release/version label in the GC selector: doing so would hide old-release
objects from collection. Retain platform type/version metadata only as an
optional release-aware `metadata.Policy` behavior when an external consumer
is verified; otherwise omit those constants and stamping behavior from v2.

Release metadata discovered from component manifests remains a separate
action output written to the instance's release-status accessor.

Release does not require special cache invalidation. The current framework
render-cache hash includes release even though none of its renderers reads that
field; this is unnecessary over-invalidation, and the newer root render-cache
hash already omits it. A render key should contain only inputs that can change
rendered output. If release is explicitly supplied as a Helm value or template
input, that typed renderer input already contributes to the key. The deploy
cache fingerprints the final desired object, so configured label or annotation
changes naturally alter the fingerprint without a separate release key.

Remove renderer-specific fields such as `Manifests`, `Templates`,
`HelmCharts`, `ManifestsBasePath`, and `ChartsBasePath` from the core request.
They currently force the reconciler types package to import Helm and rendering
details.

Optional application-specific action-to-action data uses the named extension
field rather than adding one-off fields to `Request`:

```go
const GateEntriesExtension = "upgrade.gates"

req.Extensions[GateEntriesExtension] = entries
entries, ok := req.Extensions[GateEntriesExtension].(map[string]string)
```

Extensions must not become an untyped service locator. Each key needs a
documented owner, producer, consumers, and absent-value behavior. Required
action inputs remain explicit run options or request capabilities. Desired
resources flow through `resources.Accessor`, never through an
extension key.

Do not thread action-to-action values through `context.Context`. Doing so would
force actions to return a replacement context, hide data flow, and complicate
the otherwise uniform `Execute(context.Context, *Request) error` contract.
Context remains for cancellation, deadlines, logging, and tracing; the
`Extensions` field owns optional pipeline data.

Do not use extensions for pipeline control flow. `SkipApply`, `SkipDeploy`,
and `Generated` should have neither request fields nor replacement extension
keys. Conditional execution and ordering belong to action registration.

### Action registration and conditional execution

Every action-registration method should accept the same
controller-runtime-style registration options:

```go
type ActionOptions struct {
    Name   string
    Guards []Guard
}

func (o ActionOptions) ApplyTo(target *ActionOptions) {
    // Apply explicitly configured values and clone slices.
}

type ActionOption = option.Option[ActionOptions]

func When(guard Guard) ActionOption {
    return option.FunctionalOption[ActionOptions](func(opts *ActionOptions) {
        opts.Guards = append(opts.Guards, guard)
    })
}

func WithName(name string) ActionOption {
    return option.FunctionalOption[ActionOptions](func(opts *ActionOptions) {
        opts.Name = name
    })
}

```

Registration starts with `action.Name()` and then applies options from left to
right. A non-empty `ActionOptions.Name`, whether supplied by the complete
options struct or `WithName`, becomes the effective registration name. This
name is pipeline metadata only: it does not mutate the action and has no effect
on standalone `Run` calls.

Effective action names must be non-empty and unique across the entire
reconciler, including before, main, after, cleanup, and framework-installed
actions. `Build` rejects duplicates and identifies both registrations. Global
uniqueness keeps logs, metrics, events, validation failures, and aggregated
action errors unambiguous across lifecycle phases. Registering two instances
with the same action-provided name therefore requires an override:

```go
builder.
    WithAction(check.New(endpointA), pipeline.WithName("check-endpoint-a")).
    WithAction(check.New(endpointB), pipeline.WithName("check-endpoint-b"))
```

Name resolution and duplicate validation happen before any action's optional
`Validate` method is called. This avoids reporting the same logical action
under an ambiguous identity. A duplicate-name error includes the effective
name and the phase and registration position of both conflicting actions.

Use the term `Guard` rather than predicate or condition. Controller-runtime
predicates filter watch events, while platform conditions are persisted API
observations. A guard decides whether one registered action should execute in
the current reconciliation:

```go
type Guard interface {
    Name() string
    Evaluate(context.Context, *Request) (bool, error)
}
```

Provide a named `GuardFunc` adapter for pure functions. Multiple guards use
AND semantics and are evaluated in registration order. The first `false`
result stops guard evaluation and skips the action without invoking `Execute`.
Skipping is not an action outcome: it adds no error, condition, reason, event,
or status state. A guard error fails the node and enters normal action-error
interpretation.

The pipeline does not cache or reuse guard results. It calls each guard
whenever the corresponding action registration is reached on every
reconciliation, even when the same guard value is attached to multiple
actions. `Guard.Name()` is diagnostic metadata only and is never a cache key.
If a guard represents process-lifetime singleton discovery, its implementation
may memoize explicitly—for example with `sync.Once`. Such a guard owns the
cached value and error and must be safe when concurrent reconciliations call
it; the framework does not infer cache lifetime from guard identity.

Guards are deliberately opt-in. `pipeline.When(runlevelReady)` should be used
only when skipping an action is intentional and leaves the lifecycle and every
downstream input valid. It is not the default mechanism for global readiness
or dependency checks: those checks normally belong in before actions, whose
semantic errors control whether the main phase starts.

For example, a genuinely optional main action may be guarded without adding a
flag to the request:

```go
runlevelReady := pipeline.NewGuard("runlevel-ready", checkRunlevel)

builder.
    WithAction(
        optionalMigrationAction,
        pipeline.When(runlevelReady),
    )
```

Do not guard the normal resource-production/deploy/GC chain by default. In particular,
conditionally skipping a resource-producing action can leave
`resources.Accessor` incomplete for downstream deploy or GC. When several main
actions genuinely form one optional branch, they must share the same guard and
the branch must define what its skipped resource state means. Rendering cache
hits are normal successful executions; GC does not need a `Generated` signal.
Neither the reconciler nor an action's pipeline adapter implicitly adds a
runlevel guard; `When` appears only where the controller author explicitly
registers it.

The programmatic action path is deliberately unaware of pipeline execution
policy:

- `Run` owns reusable domain execution;
- `Execute` maps `Request` to action-specific run options;
- registration APIs define phase placement, effective names, and opt-in
  guards; and
- the pipeline executor evaluates actions sequentially and records outcomes.

Registration order is execution order. V2 should not model dependencies or a
DAG preemptively. If independent or parallel branches become a real
requirement, they need a separate artifact/output design because the mutable
`Resources`, `Instance`, and `Extensions` fields are intentionally designed
for sequential execution.

### Conditions and status are reconciler status processing, not request state

`Request` must not carry a condition manager. Opted-in condition aggregation,
opted-in phase computation, and status persistence happen only after the
complete action pipeline has returned its aggregate outcome. They are
reconciler status processing, not actions and not action inputs.

Programmatic workload and OpenShift observation actions return typed
observations. Their `Execute` methods
apply those observations directly to the mutable status on `Request.Instance`
through low-level helpers:

```go
observation, err := a.Run(ctx, workload.RunOptions{
    Client:    req.Client,
    Namespace: namespace,
    Selector:  selector,
})
if err != nil {
    return err
}

conditions, ok := req.Instance.(api.ConditionsAccessor)
if !ok {
    return fmt.Errorf("%T does not implement api.ConditionsAccessor", req.Instance)
}

condition.Set(conditions, observation.Condition)
return nil
```

An action that publishes conditions therefore requires the opt-in capability
and fails clearly if used with an incompatible object. Actions that do not
publish conditions remain usable with the minimal `PlatformObject` contract.

The condition package should therefore expose two layers:

- low-level mutation and query functions over `api.ConditionsAccessor`, usable
  by pipeline adapters and programmatic callers; and
- aggregation and computation functions used by reconciler status processing to set
  framework-owned outcome conditions and aggregate/sort the actual conditions
  when `ConditionsAccessor` is implemented, compute phase when
  `PhaseStatusAccessor` is implemented, and always compute observed generation
  through `StatusAccessor`.

The low-level API should retain the useful ergonomics of the current condition
packages without requiring a manager:

```go
condition.Set(accessor, value)
condition.Mark(accessor, conditionType, metav1.ConditionTrue, opts...)
condition.MarkTrue(accessor, conditionType, opts...)
condition.MarkFalse(accessor, conditionType, opts...)
condition.MarkUnknown(accessor, conditionType, opts...)
condition.MarkFrom(accessor, conditionType, source)

condition.Find(accessor, conditionType)
condition.Remove(accessor, conditionType)
condition.IsTrue(accessor, conditionType)
condition.IsFalse(accessor, conditionType)
condition.IsPresentAndEqual(accessor, conditionType, expected)
```

Condition options such as `WithReason`, `WithMessage`,
`WithObservedGeneration`, `WithSeverity`, and `WithError` remain in
`pkg/platform/condition`. All mutation functions must share the same
last-transition-time, deep-copy, and equality semantics. Status aggregation
should delegate to these functions rather than implement a second condition
mutation path.

`MarkHealthy` and `MarkUnhealthy` depend on configured condition polarity.
They should remain aggregation operations, or accept an explicit polarity when
offered as low-level functions; they must not silently assume a polarity that
conflicts with final status aggregation.

Actions set and remove the concrete conditions they own. Registration does not
repeat condition types, severities, or failure policy. V2 does not initially
carry forward active-condition tracking, `Reset`, initialization of expected
conditions, or automatic stale-condition cleanup. A future condition-lifecycle
design can add those behaviors without putting mutable condition bookkeeping in
`Request`.

### Before, main, and after actions

The framework should expose three sequential registration phases:

```go
WithBeforeAction(action, opts...)
WithAction(action, opts...)
WithAfterAction(action, opts...)
WithCleanupAction(action, opts...)
```

All four methods accept the same `pipeline.Action` and registration-option
type. `WithName` and `When` are available in every lifecycle. Phase placement
does not create a different kind of action or a reduced registration API.
Normal execution is:

```text
all eligible before actions -> eligible main actions if allowed
-> all eligible after actions
```

Registration order is preserved within each phase. Guards are evaluated before
each registration; a false result simply skips that action. “Before” and
“after” are preferable to “precondition” and “postcondition”: the registered
values are ordinary actions, not a second check/result abstraction.

Each action owns any condition it reports. A built-in API availability action,
for example, accepts a conditions accessor as an explicit standalone input,
sets its concrete condition, and returns a semantic error:

```go
type MarkOptions struct {
    Reason             string
    Message            string
    Error              error
    ObservedGeneration *int64
    Severity           api.ConditionSeverity
}

func (o MarkOptions) ApplyTo(target *MarkOptions) {
    // Copy explicitly supplied values.
}

type MarkOption = option.Option[MarkOptions]

func WithReason(reason string) MarkOption
func WithMessage(format string, args ...any) MarkOption
func WithError(err error) MarkOption
func WithObservedGeneration(generation int64) MarkOption
func WithSeverity(severity api.ConditionSeverity) MarkOption
```

`MarkOptions` and the functional mark options configure the same fields and
compose left to right. `WithMessage` formats its arguments into the struct's
`Message` field; `ObservedGeneration` is a pointer so an explicit zero remains
distinguishable from omission.

```go
func (a *RequireAPIsAction) Run(ctx context.Context, opts ...RunOption) error {
    inputs := defaultRunOptions()
    applyRunOptions(&inputs, opts...)

    missing, err := a.findMissing(ctx, inputs.Client)
    if err != nil {
        condition.MarkUnknown(
            inputs.Conditions,
            ConditionTypeDependenciesAvailable,
            condition.WithError(err),
            condition.WithObservedGeneration(inputs.ObservedGeneration),
        )
        return fmt.Errorf("checking required APIs: %w", err)
    }

    if len(missing) > 0 {
        condition.MarkFalse(
            inputs.Conditions,
            ConditionTypeDependenciesAvailable,
            condition.WithReason("APIsUnavailable"),
            condition.WithMessage("missing APIs: %s", strings.Join(missing, ", ")),
            condition.WithObservedGeneration(inputs.ObservedGeneration),
        )
        return action.NewError("required APIs are unavailable").Terminal()
    }

    condition.MarkTrue(
        inputs.Conditions,
        ConditionTypeDependenciesAvailable,
        condition.WithObservedGeneration(inputs.ObservedGeneration),
    )
    return nil
}

func (a *RequireAPIsAction) Execute(ctx context.Context, req *pipeline.Request) error {
    return a.Run(
        ctx,
        WithClient(req.Client),
        WithConditions(req.Instance),
        WithObservedGeneration(req.Instance.GetGeneration()),
    )
}
```

Registration needs no duplicate condition configuration:

```go
reconciler.WithBeforeAction(
    requirements.RequireAPIs(requiredGVKs...),
)
```

The pipeline keeps one existing `ActionError` accumulator and calls its `Add`
method after each executed action. There is no separate execution report,
per-phase result type, or intermediate `[]error` API. `Add` continues to own
the established classification and joining behavior; its returned stop flag is
applied according to the current phase.

Phase execution differs only as follows:

- Every before action whose guards pass runs in registration order, even when
  an earlier before action fails. Their errors are aggregated. If any executed
  before action returns a plain or terminal failure, the main phase is
  suppressed only after all before registrations have been traversed.
  Non-blocking and advisory outcomes allow main execution according to their
  normal semantics.
- Main actions run in registration order. A plain or terminal failure stops
  the remaining main actions; non-blocking and advisory outcomes continue.
- Every after action whose guards pass runs in registration order regardless
  of before or main outcomes. Their errors are aggregated, but a blocking
  result never suppresses a later after registration.
- The same accumulator is carried through all three phases and interpreted
  once after status persistence using the existing semantics.

The executor is equivalent to:

```go
var outcome action.ActionError
blockMain := false

for _, current := range beforeActions {
    err, skipped := executeRegistration(ctx, req, current)
    if skipped {
        continue
    }

    var blocking bool
    outcome, blocking = outcome.Add(current.Name, err)
    blockMain = blockMain || blocking
}

if !blockMain {
    for _, current := range mainActions {
        err, skipped := executeRegistration(ctx, req, current)
        if skipped {
            continue
        }

        var stop bool
        outcome, stop = outcome.Add(current.Name, err)
        if stop {
            break
        }
    }
}

for _, current := range afterActions {
    err, skipped := executeRegistration(ctx, req, current)
    if skipped {
        continue
    }

    // After actions use finally-style execution and never short-circuit.
    outcome, _ = outcome.Add(current.Name, err)
}
```

A blocking outcome is therefore phase-sensitive: it suppresses the main phase
when returned by a before action, stops remaining main actions when returned by
a main action, and affects only the final reconciliation result when returned
by an after action.

After actions therefore have `finally`-style execution, but remain ordinary
actions with the common error contract. After the pipeline returns `outcome`,
the reconciler computes status from the final aggregate, writes the status
subresource, and only then returns:

```text
execute all eligible before actions
-> execute eligible main actions when allowed
-> execute all eligible after actions
-> compute status from the final ActionError
-> update the status subresource
-> return the interpreted result
```

Status computation is an in-memory, validated reconciler operation rather than
an internal action. Keeping it outside the action lists lets it inspect the one
final `ActionError` value after every eligible phase has run. The status write
is the final fallible operation and is attempted even when that outcome is
blocking.

For every normal reconciliation that reaches status processing, the reconciler sets
`Status.ObservedGeneration` to `Instance.GetGeneration()` regardless of whether
the aggregate action outcome is successful, blocking, terminal, non-blocking,
or advisory. Observed generation records that the controller evaluated that
generation; it does not claim that reconciliation succeeded. Conditions about
the platform object use the same generation. A failure before the normal
pipeline can evaluate the object, such as failure to install a required
finalizer, does not advance observed generation. If the status apply fails, the
new value exists only in memory and is naturally not observed by API clients.

Status persistence uses server-side apply exclusively. Consolidate the
existing framework `resources.Apply` and `resources.ApplyStatus` helpers in
`pkg/kube/resources`; do not introduce a dedicated status package or retain a
second update-, patch-, or conflict-retry-based writer. `ApplyStatus` ensures
the object's GVK, converts a deep copy to unstructured form, removes
`metadata.managedFields` and
`metadata.resourceVersion`, applies the status subresource, and converts the
server response back into the supplied object. The reconciler supplies its
stable field owner through the standard controller-runtime apply options.
Both `resources.Apply` and `resources.ApplyStatus` always use
`client.ForceOwnership`; forcing ownership is part of their contract rather
than an opt-in caller behavior. The reconciler calls `ApplyStatus` on every
normal reconciliation that reaches status processing, even when the computed
status is unchanged. V2 performs no client-side status comparison or no-op
suppression; the API server determines the effect of the SSA request. Preserve
the framework helper's SSA implementation, but not special error handling:
`ApplyStatus` returns every SSA error, including `NotFound`, through its normal
error result.

The reconciler does not inspect, classify, or join errors returned by
`ApplyStatus`. It returns the error through the ordinary controller-runtime
path, wrapping it only when additional context is actually needed:

```go
if err := resources.ApplyStatus(ctx, r.client, instance, applyOptions...); err != nil {
    return ctrl.Result{}, err
}
```

Before/main/after actions are part of normal reconciliation. Deletion cleanup
remains a separate reconciler path, so a failing before action cannot strand
deletion.

## Deletion and cleanup lifecycle

Deletion is a separate reconciler lifecycle, not another phase of the normal
before/main/after pipeline. The normal deploy and GC actions do not run after
the instance has a deletion timestamp. Resources managed by the instance are
cleaned up through Kubernetes owner references and native garbage collection;
the framework must not invoke its label-selector GC action during
the cleanup lifecycle.

Most controllers therefore need no cleanup actions and no framework
finalizer. Cleanup actions exist only for effects Kubernetes ownership cannot
represent, such as external systems or resources intentionally left without an
owner reference. An explicit resource-deletion action may be registered here
when such a case is deliberate, but it is not a default replacement for owner
references.

Cleanup uses the ordinary `pipeline.Action` contract and the same
`pipeline.Request` shape:

```go
reconciler.For(
    mgr,
    &api.MyObject{},
    reconciler.WithCleanupTimeout(10*time.Minute),
).
    WithCleanupAction(cleanupExternalState).
    Build()
```

`WithCleanupAction` is singular and repeatable, matching `WithBeforeAction`,
`WithAction`, and `WithAfterAction`. It accepts the same `WithName` and `When`
options. Cleanup actions whose guards pass execute in registration order. A
skipped cleanup action contributes no outcome and therefore does not by itself
retain the finalizer. If cleanup has dependency-order requirements, the
controller expresses the safe order when registering the actions; the
framework does not reverse or otherwise reorder them.

Cleanup actions follow the canonical action-error semantics; cleanup does not
define another set of classifiers or reinterpret returned errors. In
particular, plain and terminal errors stop the remaining cleanup actions, while
non-blocking and advisory errors allow later cleanup actions to run. The
canonical interpreter determines the returned error and requeue request.

The framework installs its finalizer only when at least one cleanup action is
registered. It adds the finalizer before beginning normal reconciliation and
returns immediately if persisting that metadata update fails. During deletion:

```text
instance has deletion timestamp
-> framework finalizer absent: return
-> construct a fresh request
-> execute cleanup actions in registration order under the action-error contract
-> interpret the cleanup outcome
-> cleanup incomplete, failed, or requests requeue: retain finalizer and return
-> cleanup complete, or enabled cleanup deadline reached: remove finalizer and return
```

An advisory outcome without a requeue request may accompany completed cleanup
and does not prevent finalizer removal. A plain, terminal, or non-blocking
failure, or any positive requeue request, means cleanup is not complete and
retains the finalizer while time remains. Failure to update the object while
removing the finalizer is returned normally so controller-runtime retries it.

Cleanup has a controller-level timeout configured with
`WithCleanupTimeout`. When positive, the absolute deadline is derived from the
object's server-assigned deletion timestamp plus that timeout; it is not reset
by reconciliation retries, controller restarts, or action-requested requeues.
The reconciler runs cleanup actions with a context capped by that deadline and
caps an explicit `RequeueAfter` to the remaining cleanup time. When the timeout
is zero, no deadline is derived, the cleanup context is not deadline-capped,
and cleanup requeues may continue until cleanup succeeds.

If the deadline has already elapsed when reconciliation starts, the reconciler
does not begin another cleanup attempt. If it expires while cleanup is
running, context cancellation allows cooperative actions to stop and no later
retry may extend the deadline. In either case, the reconciler emits a warning
event containing the incomplete cleanup diagnostics and removes its finalizer.
This deliberately prefers eventual object deletion over leaving a resource
permanently stuck in `Terminating`; external state may remain and must be
visible through logs, events, and cleanup metrics.

The framework defaults cleanup to a 10-minute timeout so registering a cleanup
action does not accidentally create an unbounded finalizer. The option has
duration-specific semantics: a positive value sets the timeout, zero disables
the deadline, and a negative value is invalid and rejected by `Build`.
Disabling the deadline is an explicit escape hatch and may leave the object in
`Terminating` indefinitely when cleanup cannot complete; it is never the
default.

The deletion request contains a newly initialized resource accessor; it is not
a persisted snapshot of resources rendered by an earlier reconciliation.
Cleanup actions must discover any required live state from their explicit
dependencies, the Kubernetes client, or the external system they clean up.
They must be idempotent because any action may run again after another action,
outcome interpretation, or finalizer update fails.

Deletion does not execute before, main, or after actions, does not synchronize
dynamic watches, and does not run normal status computation or `ApplyStatus`.
Once deletion starts, the deletion outcome and the presence of the finalizer
are the authoritative progress signals.

Retain focused built-ins such as API/CRD and object requirements under
`pkg/action/requirements`. For example, `RequireAPIs` and `ForbidAPIs` are
separate actions backed by small shared lookup helpers. They implement the
regular action interface and are registered as before actions when they gate
the entire main pipeline. Other requirements, such as a Secret, Service, or
generic object, follow the same concrete-action pattern without introducing a
general requirement engine.
Static applicability should be decided during controller setup; dynamic
applicability is expressed explicitly with `When`, including for before
actions. Actions do not hide an implicit registration guard inside `Execute`.

## Colocated pipeline adapters

Every shared first-party action package contains its own thin pipeline adapter. For
deploy this is an `Execute` method on the same `Action` returned by `deploy.New`:

```go
package deploy

func New(opts ...Option) *Action {
    options := defaultOptions()
    applyOptions(&options, opts...)
    return &Action{options: options}
}

func (a *Action) Name() string { return "deploy" }

func (a *Action) Execute(ctx context.Context, req *pipeline.Request) error {
    _, err := a.Run(ctx, &RunOptions{
        Client:    req.Client,
        Owner:     req.Instance,
        Resources: req.Resources,
    })
    return err
}
```

`Execute` must return the `Run` error unchanged so wrapping/joining precedence
remains the responsibility of the action and pipeline aggregator. Request
mapping tests belong beside `pipeline.go`; domain behavior tests exercise
`Run` beside `action.go`.

This pattern applies to every shared first-party action. Rendering is different:
the controller owns its resource-producing action because only the controller
knows how to derive renderer inputs from its API. The shared library does not
provide a generic render action or request binder.

For simple module-specific actions, callers can use `pipeline.ActionFunc`
directly. Shared functionality should not be added as a pipeline-only action.

## Action error semantics

[`docs/action-error-semantics.md`](action-error-semantics.md) is the
authoritative v2 contract. It preserves the current classifiers, precedence,
status, event, and scheduling rules while documenting the phased pipeline
continuation behavior. The v1 framework document is historical reference
material only.

In v2, “stop” is scoped by lifecycle phase:

- in `before`, a plain or terminal error prevents the main phase but does not
  suppress later eligible before actions;
- in `main`, a plain or terminal error suppresses later main actions;
- in `after`, a plain or terminal error is retained but does not suppress
  later eligible after actions; and
- in `cleanup`, the canonical deletion behavior applies: plain and terminal
  errors stop later cleanup actions, while non-blocking and advisory errors
  continue.

This phase scoping is the intentional v2 evolution of “stops the pipeline
immediately.” It changes traversal only. It does not introduce another error
type, execution report, or aggregation pass, and does not alter how the final
`ActionError` maps to conditions, events, returned errors, or requeues.

Move the implementation from `framework/controller/actions/errors` to
`pkg/action`:

```go
action.NewError("dependency unavailable").
    Terminal().
    WithRequeueAfter(time.Minute)
```

Every action returns errors according to that contract. The reconciler remains
responsible for applying it, updating conditions, emitting events, and deciding
between a returned error and `RequeueAfter`. Programmatic callers may inspect
the same error with `errors.As` but are not forced to use controller-runtime
scheduling.

The deprecated `StopError` and `RequeueAfterError` types should not be carried
into v2. Migration documentation should map them to terminal and advisory
`ActionError` values.

Pipeline action `Execute` methods must return `Run` errors unchanged so
wrapping/joining precedence remains the responsibility of the action and
pipeline aggregator.

## Renderer integration

V2 should not define another renderer interface or mirror the manifest-kit
option surface. Controllers use the manifest-kit engine and concrete renderers
directly:

```go
helmRenderer, err := helm.New(
    []helm.Source{{
        Chart:       chartPath,
        ReleaseName: "my-component",
    }},
    helm.WithCache(),
)
if err != nil {
    return err
}

kustomizeRenderer, err := kustomize.New(
    []kustomize.Source{{Path: overlayPath}},
    kustomize.WithCache(),
)
if err != nil {
    return err
}

templateRenderer, err := gotemplate.New(
    []gotemplate.Source{{
        FS:   templates,
        Path: "*.yaml.tmpl",
    }},
    gotemplate.WithCache(),
)
if err != nil {
    return err
}

renderer, err := manifestengine.New(
    manifestengine.WithRenderer(helmRenderer),
    manifestengine.WithRenderer(kustomizeRenderer),
    manifestengine.WithRenderer(templateRenderer),
)
```

This uses the common renderer contract, filters, transformers, metrics, and
cache implementation already supplied by manifest-kit. V2 does not rename
`Process`, recreate `Source` or option types, hide the libraries behind an ODH
interface, or add a second cache.

Rendering remains controller-specific pipeline behavior. The module controller
should be a struct that owns its initialized renderer and other module-specific
dependencies. Custom actions are methods on that controller rather than
additional action structs. A rendering method derives values from the module
API, calls the configured engine, converts the returned unstructured values to
the shared `resources.List`, and explicitly writes them to the accessor:

```go
type Controller struct {
    renderer *manifestengine.Engine
}

var requiredGVKs = []schema.GroupVersionKind{
    gvk.Deployment,
    gvk.ServiceAccount,
}

func NewController(renderer *manifestengine.Engine) *Controller {
    return &Controller{renderer: renderer}
}

func (c *Controller) renderResources(
    ctx context.Context,
    req *pipeline.Request,
) error {
    values, err := valuesFrom(req.Instance)
    if err != nil {
        return err
    }

    rendered, err := c.renderer.Render(ctx, enginerender.WithValues(values))
    if err != nil {
        return err
    }

    objects := make(resources.List, len(rendered))
    for i := range rendered {
        objects[i] = &rendered[i]
    }

    req.Resources.Set(objects)
    return nil
}
```

The method is registered through the lightweight named function adapter:

```go
controller := NewController(renderer)

renderResources := pipeline.ActionFunc{
    ActionName:  "render-resources",
    ExecuteFunc: controller.renderResources,
}
```

The same pattern applies to other controller-specific actions. Shared actions
such as deploy and GC remain reusable concrete action types. Dependencies stay
on the controller struct and are never added to `pipeline.Request` merely so a
custom action can reach them.

A controller may instead use one concrete renderer directly when it does not
need a multi-renderer engine. Manifest-kit cache options are configured on the
concrete renderer. Cache-hit state never controls deploy or GC, and
`pipeline.Request` has no `Generated` field.

A local wrapper is justified only when it adds a verified ODH requirement that
cannot be expressed with manifest-kit. It must remain narrow, document the
upstream gap, and avoid forwarding the complete constructor, source, transform,
or cache API. Prefer contributing generally useful missing behavior upstream
and deleting the adapter once available.

Apply ordering remains deploy policy. Controller rendering actions must not
install manifest-kit's apply-order post-renderer by default; the deploy action
sorts the final combined desired collection before applying it.

## Concrete actions

### Deploy

Use the root `pkg/deploy.Deployer` as the starting implementation. Port the
framework-only behavior that is still required, including continue-on-error,
default part-of labeling, monitoring customizers, legacy ownership cleanup,
and CRD handling. Do not keep a second deploy loop in `Execute`.

Rename `Deployer` to `Action` inside `pkg/action/deploy`; the package already
communicates the operation. `deploy.New()` is immediately usable and returns
`*Action` without error. Its defaults are:

- server-side apply;
- Kubernetes dependency/apply-order sorting;
- field owner derived from the owner kind, with the stable platform field
  owner retained for CRDs;
- the owner-derived `platformmetadata.DefaultPolicy()`;
- owner references whenever Kubernetes permits them;
- the verified Deployment, aggregated ClusterRole, and observability merge
  behavior currently expected by module controllers;
- the canonical managed-resource opt-out annotation;
- fail on the first resource error; and
- no process-local deploy cache unless explicitly enabled.

These defaults make both `deploy.New().Run(...)` and
`reconciler.WithAction(deploy.New())` useful without options. Options are for
intentional deviations. `WithContinueOnError` returns a joined error preserving
every failed resource.

By default, deploy applies normal owner references and the shared
`platformmetadata.DefaultPolicy()`. The policy stamps the owner-derived
`part-of` label and instance name, namespace, UID, and generation annotations
on every desired object. Deploy writes the decorated desired snapshot back
through `resources.Accessor`, so later actions see exactly the metadata that was
deployed. `WithMetadataPolicy` replaces this default and must apply uniformly
to CRDs and ordinary resources.

### Garbage collection

Use the root collector as the starting implementation. Its existing split
between construction options and `RunParams` already approximates the v2
model. Convert `RunParams` to controller-runtime-style `RunOptions`, return a
result with discovery/list/delete counts, and merge framework-only predicates
and rule evaluation.

GC delegates the set of Kubernetes types to a small discovery contract:

Plain dynamic discovery is intentionally uncached: every `Discover` call reads
the server, so standalone use remains correct without controller
infrastructure. The specialized discovery client is captured by the discoverer
rather than carried through the pipeline request:

```go
typeDiscovery := gc.DynamicDiscovery(discoveryClient)
gcAction := gc.New(typeDiscovery)
```

Framework wiring opts into a lazy cache with event-driven invalidation:

```go
typeDiscovery := gc.DynamicDiscovery(
    discoveryClient,
    gc.WithEventInvalidation(mgr),
)
```

The equivalent complete-struct form is:

```go
typeDiscovery := gc.DynamicDiscovery(
    discoveryClient,
    gc.DynamicDiscoveryOptions{
        EventInvalidationManager: mgr,
    },
)
```

`WithEventInvalidation` only records the manager during construction. On the
first `Discover`, the dynamic implementation attaches handlers to the manager's
shared CRD informer and, when aggregated APIs are relevant, its APIService
informer; waits for initial synchronization; invalidates once; and populates
the discovery cache. Subsequent add, update, and delete events invalidate both
the discoverer's GVK snapshot and any underlying client-go discovery cache.
Update events include the CRD transition to `Established`, avoiding a cache
refill that occurs after object creation but before the new API is served.
Informer registration and synchronization failures are returned by `Discover`,
not hidden or moved into the constructor.

The cached implementation is concurrency-safe and serializes refresh with
invalidation so a refresh started before an event cannot publish stale data
after that event. It also applies a bounded maximum age as a fallback for missed
events. The wrapper manager creates one instance, shares it across controller
GC actions, and may expose it through `Discovery()`; no discovery service,
manager, invalidator, or watch registrar is added to `pipeline.Request`.

Dynamic discovery enumerates the server's listable API resource types. A
finite static set is configured by passing the alternative implementation:

```go
gc.New(
    gc.StaticDiscovery(
        appsv1.SchemeGroupVersion.WithKind("Deployment"),
        corev1.SchemeGroupVersion.WithKind("ConfigMap"),
    ),
)
```

`StaticDiscovery` returns a `TypeDiscoveryFunc`-backed implementation, copies
the supplied GVKs, and performs no server API enumeration. An empty static list
is rejected by the GC action's optional `Validate` method during pipeline build
and independently by `Run` before I/O. Callers may pass any concurrency-safe
`TypeDiscovery` implementation.

`gc.New(typeDiscovery, opts...)` requires the immutable discovery strategy as
a positional dependency and uses the common action functional-option pattern
for optional GC policy. `TypeDiscovery` is therefore not a field in
`gc.Options`, and there is no `gc.WithTypeDiscovery` option. Construction
returns `*Action` without error. The positional argument makes accidental
omission impossible; a nil or typed-nil implementation is still rejected by
`Validate` during pipeline build and independently by `Run` before I/O. The
action uses the ordinary
controller-runtime `client.Client` from `RunOptions` to resolve each discovered
GVK through its REST mapper, list unstructured objects, perform API-backed
authorization checks, and delete selected objects. The specialized discovery
client is never exposed to the action, run options, or pipeline request.

After type discovery returns resources, every implementation uses the same GC
machinery:
type predicates, RBAC authorization for list/delete, namespace scoping,
metadata selection, exact controller-owner verification, desired-set diff,
unremovable types, and deletion. Static discovery skips API type enumeration;
it does not bypass authorization or ownership safety. Uncached dynamic
discovery refreshes the server resource set on each run. Event-invalidated
dynamic discovery reuses its snapshot until an informer event or the maximum
age marks it stale.

GC otherwise defaults to the owner-derived metadata policy, desired-set
comparison, owner safety checks, RBAC-aware filtering, foreground deletion,
and the CRD/Lease unremovable set. Metrics and additional predicates are
opt-in. Namespace scope is derived from the per-run owner unless explicitly
overridden.

Replace its hard-coded release/generation annotation predicate with the shared
metadata policy plus a desired-set diff. `RunOptions` includes
`resources.Accessor`; GC lists objects using `metadata.Policy.Selector`, skips
every object not controlled by the supplied owner, and indexes desired objects
by GVK, namespace, and name. Only after that ownership check can an absent
desired identity or outdated `metadata.Policy.Matches` result classify the
owned object as stale. This makes rendered desired state authoritative while
allowing a custom release-aware policy, and removes the direct `Version` and
`PlatformType` run parameters.

GC uses `platformmetadata.DefaultPolicy()` unless
`gc.WithMetadataPolicy(...)` replaces it. It uses `Policy.Selector` to narrow
API listing, exact controller owner references as the mandatory deletion
boundary, `Policy.Matches` to detect outdated lifecycle metadata, and
`resources.Accessor` to determine whether each owned candidate remains in
desired state. A selected object without a matching controller owner reference
is always skipped. Resources that cannot legally carry that owner reference
are outside generic GC and require an explicit lifecycle strategy.

The controller framework may inject one composite policy instance into both
deploy and GC. Do not expose an independent selector option that can diverge
from the deploy policy. Passing nil to `WithMetadataPolicy` leaves the safe
default in place rather than creating an implicit `labels.Everything()`
selector.

GC runs only after resource production has completed successfully according to
the common action-error semantics. An empty but successful desired set means
“remove all selected managed resources”; a render failure prevents GC from
interpreting an incomplete set as desired state.

GC remains a distinct action. The controller author must register it after all
actions that produce or transform the desired resource accessor; the pipeline
preserves that registration order and does not detect, reorder, or otherwise
special-case GC.

### Delete resources

Extract the framework implementation into `pkg/action/delete`. Namespace,
resource types, labels, and client become run inputs or immutable policy based
on whether they vary per reconciliation. `Execute` resolves dynamic values
from the pipeline request and invokes `Run`.

### Additional requirements

Extract remaining environment checks into `pkg/action/requirements`. Keep
`RequireAPIs` and `ForbidAPIs` as separate concrete actions, and add focused
object requirements such as `RequireSecret`, `RequireService`, or
`RequireObject` only when consumers need them. They receive a narrow
controller-runtime client in `Run`, set their own concrete condition when
applicable, and return the existing action-error semantics. Required
dependencies are blocking by default; forbidden APIs represent a terminal
incompatibility; optional object checks may use advisory or non-blocking
semantics where that is intrinsic to the action. Do not add a configurable
severity framework until a real consumer needs it. Unexpected API failures
remain plain wrapped errors.

### Dynamic ownership

Dynamic watch registration is controller topology maintenance, not a reusable
standalone action. Do not expose a public ownership action, `WatchRegistrar`, or
controller capability through `pipeline.Request`.

When dynamic ownership is enabled, the reconciler appends a private action to
the end of the after-action list after all user-provided after actions:

```go
if options.DynamicOwnership {
    afterActions = append(afterActions, pipeline.ActionFunc{
        ActionName: "synchronize-dynamic-watches",
        ExecuteFunc: func(ctx context.Context, req *pipeline.Request) error {
            return reconciler.syncDynamicWatches(
                ctx,
                req.Instance,
                req.Resources.All(),
            )
        },
    })
}
```

The private action captures the built controller and reconciler infrastructure
directly. It inspects the final resource snapshot, derives the required owned,
annotation-routed, and CRD watches, and registers only missing watches. Static
watches seed the internal registered set; configured exclusions remain
reconciler policy. Registration must be idempotent, record a watch only after
successful registration, and protect mutable state for concurrent reconciles.

Watch synchronization is independent of action outcomes. The private action is
unguarded and runs whenever the normal reconciliation reaches the after
lifecycle, including when a before, main, or user after action failed, was
skipped, or requested a requeue. It does not inspect the aggregate outcome,
deploy result, apply count, or a generated/success marker. It derives watches
from whatever resources are present in the accessor at that point.

A complete render is published atomically, so a render failure before
publication contributes no new resource types. Deploy publishes its complete
normalized and metadata-decorated desired snapshot before API writes; a skipped
or partially failed apply can therefore still cause the desired GVK watches to
be registered. Watch registration is about observing possible owned resources,
not proving that each object was successfully applied. An empty accessor simply
adds no dynamic watches.

The synchronization action's own error follows the canonical action-error
semantics and participates in status processing, but no other action's outcome
suppresses its invocation. It is installed only for normal reconciliation when
dynamic ownership is enabled, not on the deletion/cleanup path.

This framework-managed action lives as unexported code in
`pkg/controller/reconciler`; it is not subject to the rule that shared public
actions expose a standalone `Run` method and does not expose a public
standalone action or registrar contract. Deploy only applies resources and
publishes its decorated snapshot. It does not query or mutate controller watch
state.

### Workload observations and release discovery

Deployment checks should return typed workload observations or `api.Condition`
values. They should not receive a condition manager. The action's `Execute`
method applies the returned condition to `req.Instance`
with `condition.Set`.

Release discovery should return `api.ReleaseStatus`; `Execute` stores it in the
instance's release status pointer. File parsing and release selection stay in
the programmatic `Run` path.

Neither family writes the Kubernetes status subresource. The reconciler owns
the final write through `pkg/kube/resources.ApplyStatus` after condition and
release results have been applied through the object's separate status
capabilities.

## Reconciler setup

Keep a fluent builder for controller topology—primary resources, watches, raw
sources, and predicates—because controller-runtime uses the same model and
those calls describe an ordered controller graph.

The public construction boundary should remain small:

```go
func For(
    mgr manager.Manager,
    prototype api.PlatformObject,
    opts ...Option,
) *Builder

func (b *Builder) Build() error
```

The builder does not need a type parameter: `api.PlatformObject` already
provides the object, metadata, and deep-copy capabilities used by setup and
reconciliation. The prototype's dynamic type is the primary type registered
with controller-runtime.

`prototype` identifies the primary Kubernetes type. `For` defensively copies
it and resolves its GVK from the manager scheme. `Build` validates the
prototype, reconciler options, effective action names, optional action
validators, watches, and predicates before registering the controller with the
manager. It returns only an error because callers do not need the private
pipeline executor or controller-runtime controller after registration. It does
not accept a context: building controller topology is synchronous setup, not a
reconciliation operation.

The prototype is never reused as mutable reconciliation state. For every
request, the reconciler obtains a fresh instance through the Kubernetes
object's generated deep-copy contract rather than reflection:

```go
func newInstance(prototype api.PlatformObject) (api.PlatformObject, error) {
    instance, ok := prototype.DeepCopyObject().(api.PlatformObject)
    if !ok {
        return nil, fmt.Errorf(
            "deep copy of %T does not implement api.PlatformObject",
            prototype,
        )
    }

    return instance, nil
}
```

`Build` checks this once during setup. The hot reconciliation path then creates
the fresh object, loads it directly by `ctrl.Request.NamespacedName`, and
returns `client.IgnoreNotFound(err)` when it has been deleted. It ensures the
loaded object has its GVK before constructing `pipeline.Request`.

The internal `Reconcile` flow remains conventional and linear:

1. Create a fresh instance from the validated prototype.
2. Load it by the incoming namespaced name and return cleanly on `NotFound`.
3. If it is deleting, execute only the cleanup lifecycle described above.
4. Otherwise, handle the framework finalizer when cleanup actions require one.
5. Create one request with the manager client, loaded instance,
   `resources.New(nil)`, and an initialized `pipeline.Extension` map.
6. Execute before, main, and after actions with the existing single
   `ActionError` accumulator.
7. Compute opted-in status fields, always call `resources.ApplyStatus`, and
   then interpret the action outcome as the controller-runtime result.

No module callback is needed to create or load the primary instance. Actions
start only after the client has returned the authoritative object, including
its UID, generation, deletion timestamp, and resource version.

The core reconciler makes no singleton assumption and never lists all primary
objects to locate one. It works for cluster-scoped, namespaced, singleton, and
multi-instance APIs. Singleton admission remains in
`pkg/kube/admission/singleton`; `pkg/kube/singleton` remains an explicit helper
for callers that genuinely need singleton lookup outside the normal reconcile
path. Watches are responsible for producing the correct namespaced name,
using focused handlers such as owner-annotation mapping or `handler.ToNamed`
when an event must target a known singleton.

Controller identity and instance routing must not share one option. Replace
the current ambiguous `WithInstanceName` builder setting with
`WithControllerName`, used only for the controller-runtime name, logs, events,
and metric labels. The default remains derived from the primary GVK. A known
singleton instance name belongs in the event handler that maps a watched
object to a reconcile request; it does not change how primary-resource events
are loaded.

Use functional options for reconciler policy and concrete actions. Do not use
action builders. Action constructors are total, so concrete actions can be
registered inline. Before constructing reconcilers, distribution-specific
bootstrap code computes one `api.PlatformProfile`. The same immutable value may
be passed explicitly to ordinary functions and action/policy constructors. A
reconciler receives a defensive copy only to project it into status for objects
that implement `api.PlatformProfileAccessor`:

```go
type Options struct {
    CleanupTimeout      *time.Duration
    DefaultRequeueAfter time.Duration
    // Other optional reconciler policy.
}

func (o Options) ApplyTo(target *Options) {
    if o.CleanupTimeout != nil {
        target.CleanupTimeout = new(*o.CleanupTimeout)
    }

    // Apply every other field according to its documented zero semantics.
}

type Option = option.Option[Options]

func WithCleanupTimeout(timeout time.Duration) Option {
    return Options{CleanupTimeout: new(timeout)}
}

func WithDefaultRequeueAfter(interval time.Duration) Option
```

The reconciler constructor initializes `CleanupTimeout` to a pointer containing
10 minutes before applying options. Its presence semantics are explicit:

- `CleanupTimeout: nil` in an option struct preserves the initialized
  default;
- `CleanupTimeout: new(time.Duration(0))` disables the deadline;
- a pointer to a positive duration overrides the default; and
- a pointer to a negative duration fails build validation.

`WithCleanupTimeout(timeout)` creates the same present value as
`Options{CleanupTimeout: new(timeout)}`. The action copies the
pointed-to duration while applying the option and stores a resolved duration,
so it neither retains caller-owned pointer storage nor needs pointer checks in
the reconciliation loop.

The reconciler's complete `Options` struct and its functional options compose
through the same constructor option list. Fluent `WithBeforeAction`,
`WithAction`, `WithAfterAction`, `WithCleanupAction`, watch, and predicate
methods remain topology-builder operations rather than constructor functional
options.

The module controller and its `renderResources` method are registered by the
single `controller.New(mgr, opts...)` constructor shown in the
end-to-end example below. Reusable built-in actions remain concrete action
values, while controller-specific actions remain methods on the controller
struct. These actions run in exactly the order registered there. API
requirements always run; their semantic result determines whether the
unguarded main chain starts. Framework-managed dynamic ownership runs as an
after action and observes the deployed resource snapshot independently of
earlier outcomes.

Once every after action has run, the pipeline returns its aggregate outcome and
the reconciler computes status, copies the configured startup profile when the
object opts in, and persists status before returning the reconciliation result.
The profile is not an action, request field, or per-reconcile discovery result.

`Build` calls `Validate` on each registered action that implements
`pipeline.Validator` and fails setup for invalid pipeline configuration.
Actions without static setup constraints implement only `pipeline.Action`.
Runtime errors are reserved for cluster state and per-reconcile inputs.
The module controller is constructed first with its manifest engine and other
module dependencies; `New` then registers its named method values alongside
built-in actions. The framework reconciler does not own a generic
renderer field and the module controller does not need to implement
`reconcile.Reconciler`; the private framework reconciler registered by `Build`
owns the lifecycle.

## End-to-end module reconciler example

The following example shows the intended shape of a real module controller. It
uses a generated Kubernetes API type called `Component`, constructs the
manifest-kit Helm engine once during controller construction, keeps custom
actions as methods on the controller struct, and registers reusable deploy and
GC actions directly.

The generated `Component` type is assumed to implement `api.PlatformObject`.
Its status implements the common status and release-status accessors, and it
may additionally implement `api.ConditionsAccessor` and
`api.PlatformProfileAccessor`:

```go
// Component is the generated API type for this module. Generated methods and
// API registration boilerplate are omitted here.
type Component struct {
    metav1.TypeMeta   `json:",inline"`
    metav1.ObjectMeta `json:"metadata,omitempty"`

    Spec   ComponentSpec   `json:"spec,omitempty"`
    Status ComponentStatus `json:"status,omitempty"`
}

type ComponentSpec struct {
    Image    string `json:"image"`
    Replicas int32  `json:"replicas,omitempty"`
}

type ComponentStatus struct {
    api.Status        `json:",inline"`
    api.ReleaseStatus `json:",inline"`
    Platform          *api.PlatformProfile `json:"platform,omitempty"`
}
```

### Controller construction

The controller owns the renderer because the chart, release name, and chart
configuration are module-specific. The Helm renderer and manifest engine are
created once, before controller registration and before any reconcile starts.
Renderer construction may return an error because an invalid chart source is a
startup configuration error. This is separate from action construction:
`deploy.New()` and `gc.New(...)` are total constructors with sensible defaults.

```go
package controller

import (
    "context"
    "fmt"

    manifestengine "github.com/k8s-manifest-kit/engine/pkg"
    manifestrender "github.com/k8s-manifest-kit/engine/pkg/render"
    manifesttypes "github.com/k8s-manifest-kit/engine/pkg/types"
    helm "github.com/k8s-manifest-kit/renderer-helm/pkg"

    "github.com/opendatahub-io/odh-platform-utilities/api"
    "github.com/opendatahub-io/odh-platform-utilities/pkg/action/deploy"
    "github.com/opendatahub-io/odh-platform-utilities/pkg/action/gc"
    "github.com/opendatahub-io/odh-platform-utilities/pkg/action/requirements"
    "github.com/opendatahub-io/odh-platform-utilities/pkg/controller/pipeline"
    "github.com/opendatahub-io/odh-platform-utilities/pkg/controller/reconciler"
    "github.com/opendatahub-io/odh-platform-utilities/pkg/kube/gvk"
    "github.com/opendatahub-io/odh-platform-utilities/pkg/option"

    metav1 "k8s.io/apimachinery/pkg/apis/meta/v1"
    "k8s.io/apimachinery/pkg/runtime/schema"
    "k8s.io/client-go/discovery"
    "sigs.k8s.io/controller-runtime/pkg/manager"
)

type Controller struct {
    renderer *manifestengine.Engine
}

type Options struct {
    ChartPath         string
    ControllerName   string
    ReleaseName      string
    ReleaseNamespace string
    PlatformProfile  api.PlatformProfile
}

func (o Options) ApplyTo(target *Options) {
    // Copy explicitly supplied fields and clone profile annotations.
}

func (o Options) Validate() error {
    if o.ChartPath == "" {
        return fmt.Errorf("component chart path is required")
    }
    if o.ControllerName == "" {
        return fmt.Errorf("controller name is required")
    }
    if o.ReleaseName == "" {
        return fmt.Errorf("release name is required")
    }
    if o.ReleaseNamespace == "" {
        return fmt.Errorf("release namespace is required")
    }
    return nil
}

type Option = option.Option[Options]

func WithChartPath(path string) Option
func WithControllerName(name string) Option
func WithReleaseName(name string) Option
func WithReleaseNamespace(namespace string) Option
func WithPlatformProfile(profile api.PlatformProfile) Option

func New(
    mgr manager.Manager,
    opts ...Option,
) (*Controller, error) {
    options := Options{
        ControllerName:   "component-controller",
        ReleaseName:      "component",
        ReleaseNamespace: "component-system",
    }
    for _, opt := range opts {
        opt.ApplyTo(&options)
    }
    if err := options.Validate(); err != nil {
        return nil, fmt.Errorf("validating controller options: %w", err)
    }

    renderer, err := helm.NewEngine(
        helm.Source{
            Chart:               options.ChartPath,
            ReleaseName:         options.ReleaseName,
            ReleaseNamespace:    options.ReleaseNamespace,
            ProcessDependencies: true,
        },
        helm.WithCache(),
    )
    if err != nil {
        return nil, fmt.Errorf("creating Helm render engine: %w", err)
    }

    controller := &Controller{renderer: renderer}

    discoveryClient, err := discovery.NewDiscoveryClientForConfig(mgr.GetConfig())
    if err != nil {
        return nil, fmt.Errorf("creating discovery client: %w", err)
    }

    typeDiscovery := gc.DynamicDiscovery(
        discoveryClient,
        gc.WithEventInvalidation(mgr),
    )

    err = reconciler.For(mgr, &Component{}).
        WithControllerName(options.ControllerName).
        WithPlatformProfile(options.PlatformProfile).
        WithBeforeAction(requirements.RequireAPIs(requiredGVKs...)).
        WithActionFunc(controller.renderResources).
        WithAction(deploy.New()).
        // GC is last among the user-registered desired-resource actions.
        WithAction(gc.New(typeDiscovery)).
        // Dynamic ownership is installed by the framework as an after action.
        WithDynamicOwnership().
        Build()
    if err != nil {
        return nil, fmt.Errorf("building component controller: %w", err)
    }

    return controller, nil
}
```

`helm.NewEngine` is the appropriate convenience constructor when the controller
has one Helm source. It wraps the concrete Helm renderer and the generic
manifest engine. The explicit `helm.New` plus `manifestengine.New` form shown
in the renderer integration section remains useful when composing Helm with
Kustomize, Go templates, or multiple renderer instances. In either form, the
engine is immutable after construction and safe to reuse across reconciles.
Render-time values are supplied by the action because they depend on the
current `Component` instance; chart sources and renderer configuration do not
belong in `pipeline.Request`.

### Custom action methods

The custom rendering action is a method on `Controller`. It reads the
authoritative API object from the request, derives Helm values, renders the
chart, deep-copies the returned objects into the shared resource accessor, and
only publishes the snapshot after rendering succeeds:

```go
func (c *Controller) renderResources(
    ctx context.Context,
    req *pipeline.Request,
) error {
    component, ok := req.Instance.(*Component)
    if !ok {
        return fmt.Errorf("expected *Component, got %T", req.Instance)
    }

    values := manifesttypes.Values{
        "component": map[string]any{
            "name":      component.Name,
            "namespace": "component-system",
            "image":     component.Spec.Image,
            "replicas":  component.Spec.Replicas,
        },
    }

    rendered, err := c.renderer.Render(
        ctx,
        manifestrender.WithValues(values),
    )
    if err != nil {
        return fmt.Errorf("rendering component manifests: %w", err)
    }

    // Append only after the complete render has succeeded. The manifest-kit
    // engine returns values, so append deep-copied objects one at a time to
    // satisfy Accessor.Append(...client.Object).
    for i := range rendered {
        req.Resources.Append(rendered[i].DeepCopy())
    }

    return nil
}
```

The method is adapted to the pipeline with the named function adapter. The
adapter contains only request mapping; it does not create a second rendering
implementation:

```go
func renderAction(c *Controller) pipeline.Action {
    return pipeline.Wrap(c.renderResources)
}
```

Additional module-specific actions follow the same rule: put reusable logic in
methods on `Controller`, keep dependencies such as clients, renderers, and
module configuration on the struct, and expose only a thin `ActionFunc`
registration when the action is pipeline-specific. Shared domain actions
remain reusable concrete values such as `deploy.New()` and `gc.New(...)`.

### Manager wiring and pipeline registration

`New` receives the controller-runtime manager as its required dependency and
performs the complete setup: it applies controller options, constructs the
manifest engine, creates event-invalidated dynamic discovery, builds the
reconciler, and registers the pipeline. There is no second setup lifecycle
method.

`RequireAPIs` (and `ForbidAPIs` when a module has an explicitly incompatible
API) are ordinary before actions: they set their concrete conditions and return
semantic errors when their checks fail. A blocking before outcome suppresses
the main phase, so neither rendering, deploy, nor GC runs against an
incompatible cluster.

A typical process bootstrap computes the platform profile once and passes it
to the constructor as an option:

```go
profile, err := discoverPlatformProfileAtStartup(ctx, mgr.GetClient())
if err != nil {
    return fmt.Errorf("discovering platform profile: %w", err)
}

if _, err := controller.New(
    mgr,
    controller.WithChartPath(chartPath),
    controller.WithControllerName("component-controller"),
    controller.WithPlatformProfile(profile),
    controller.WithReleaseNamespace("component-system"),
); err != nil {
    return fmt.Errorf("creating component controller: %w", err)
}
```

`discoverPlatformProfileAtStartup` represents distribution-specific bootstrap
code; it is intentionally not a framework API. The profile is immutable and
is used for optional status projection, never as a desired-state input.

### Reconcile behavior of the example

The resulting execution is:

```text
require APIs
    -> render Helm chart into resources.Accessor
    -> deploy desired resources with the default metadata policy
    -> garbage-collect owned resources absent from the desired snapshot
    -> framework-managed dynamic ownership synchronization (if enabled)
    -> compute opted-in status fields
    -> ApplyStatus
    -> interpret the final ActionError
```

The important invariants are:

- the Helm engine is initialized once, not once per reconcile;
- every action has a named pipeline registration, while action ordering is
  visible in `controller.New`;
- render failure leaves the accessor incomplete and therefore prevents GC;
- deploy and GC share the default owner-derived metadata policy;
- GC uses dynamic discovery with event invalidation in the controller, while a
  standalone caller can use uncached dynamic discovery or static discovery;
- the framework owns status persistence and dynamic watch synchronization; and
- the custom action remains testable as a method without constructing a
  reconciler or a `ReconciliationRequest`.

## Migration strategy

V2 should be built in dependency order rather than moving entire directories
at once.

### Phase 0: consumer and behavior audit

- Inventory every exported v1 symbol and its repository-local call sites.
- Check known module-controller repositories for imports so the redesign has a
  complete consumer and behavior inventory.
- Give every current production capability a provisional v2 use case and
  owning context.
- Classify symbols as `reshape`, `consolidate`, `internalize`, or
  `compatibility-only`. Do not use this pre-redesign audit to drop a
  capability.
- Record source compatibility breaks in the migration guide without adding
  forwarding packages to v2.

### Phase 1: foundation

- Create the `/v2` module path and single-module build.
- Set the module language version to Go 1.26 and update the Makefile, CI, and
  development toolchain pin to a supported Go 1.26 patch release.
- Establish `api`, `pkg/platform/*`, and the focused `pkg/kube/*` capability
  packages; do not create a local renderer hierarchy.
- Introduce `resources.Accessor` under `pkg/kube/resources`, its default
  `resources.Collection` implementation, and accessor-based resource helpers.
- Add architecture tests for forbidden dependency directions.
- Add a source-level assertion that only `pipeline.go` files under
  `pkg/action/*` reference `pipeline.Request`.
- Add a generated consumer CR fixture for API/kubebuilder/deepcopy validation.

### Phase 2: renderers

- Replace local Helm, Kustomize, and Go-template renderer implementations with
  direct imports of their manifest-kit renderer modules.
- Verify filesystem, plugin, load-restriction, template-function, transform,
  source-annotation, and cache parity against actual consumers.
- Contribute generally useful gaps upstream; retain a narrow local adapter only
  for a verified ODH-specific requirement.
- Add a controller-owned rendering-action example that composes manifest-kit
  renderers and writes their output to `resources.Accessor`.

### Phase 3: programmatic actions

- Move deploy and GC first because standalone implementations already exist.
- Port framework-only policies behind explicit options.
- Extract delete, requirements, workload, OpenShift, and release actions.
- Require programmatic tests that invoke `Run` without constructing a pipeline
  request.

### Phase 4: pipeline adapters and reconciler

- Introduce `pkg/controller/pipeline` as the owner of `Request`, extensions,
  named action registrations, guards, and before/main/after phase execution.
- Introduce `pkg/controller/reconciler` as the owner of the builder and the
  controller-runtime lifecycle. Keep `pkg/controller` free of Go source files;
  it is only the parent directory for focused controller packages.
- Replace the reflection-based instance factory with prototype
  `DeepCopyObject`, load primary resources directly from the incoming request,
  and keep singleton listing out of the reconciler path.
- Make `Build()` perform controller registration and return only `error`;
  remove its unused context and do not expose the private reconciler or built
  controller.
- Replace ambiguous `WithInstanceName` setup with controller-only
  `WithControllerName`; explicit event handlers own routing to known instance
  names.
- Introduce before, main, and after action phases using the same action and
  error contracts. Run every before and after action, aggregate all their
  errors, and short-circuit only the main phase.
- Add a thin `pipeline.go` adapter to each action package and make its concrete
  action satisfy `pipeline.Action`.
- Remove `Request.Controller`. Move dynamic ownership out of deploy and install
  framework-managed dynamic-watch synchronization as the final after action
  when the feature is enabled.
- From the complete pipeline outcome, compute conditions and phase outside the
  action lists only for objects that opt into their accessor interfaces; always
  compute observed generation, then perform the status-subresource write.
- Port the reconciler and preserve `ActionError` classification and result
  interpretation while applying the documented v2 phase-scoped continuation
  behavior.
- Keep [`docs/action-error-semantics.md`](action-error-semantics.md)
  authoritative, with the v2 package names and the before/main/after/cleanup
  stop scopes alongside the unchanged classifier precedence and scheduling
  rules.
- Replace the finalizer-action list with repeatable `WithCleanupAction`
  registration. Keep deletion separate from the normal pipeline, execute
  cleanup actions under the canonical action-error semantics, and rely on
  owner references rather than invoking deploy or GC during deletion.
- Remove renderer-specific fields from the pipeline request.

### Phase 5: remove duplicates

- Delete the nested `framework/go.mod` and its replace directive.
- Remove old root/framework implementations after the retained behavior's
  acceptance tests pass.
- Rewrite the `framework/testing` harness and module metadata as needed to use
  v2 imports; preserving its current APIs and local replace directives is not a
  compatibility requirement.
- Update examples and docs to `/v2` imports.
- Publish a symbol-by-symbol migration guide.

### Phase 6: post-redesign capability review

- Evaluate capabilities only after the coherent v2 implementation and its
  consumer migrations are visible.
- Remove a capability only with evidence that it has no remaining use, is
  fully replaced upstream, or has become unnecessary because of the v2
  architecture.
- Treat this as a separate decision with its own migration and compatibility
  assessment; it must not delay or distort the package redesign.

`flakiness/` remains untouched throughout these phases. `framework/testing/`
is a migration consumer rather than part of the public v2 package design and
may be replaced or rewritten.

## Compatibility and versioning

Because this is a Go v2 module, the `/v2` suffix is mandatory in the module
path and imports. V1 remains available for existing consumers; v2 does not
need forwarding packages that preserve the old tree.

Breaking changes that should be explicit in release notes:

- one module replaces root plus framework modules;
- all imports move to `/v2`;
- `api/common` and `framework/api` become `api`;
- `PlatformObject` accessors are reduced;
- actions return concrete instances with both programmatic `Run` and pipeline
  `Execute` entry points;
- colocated pipeline adapters replace framework action implementations and
  the parallel controller-action package hierarchy;
- renderer package-level convenience functions are removed;
- legacy `StopError` and `RequeueAfterError` are removed;
- package paths are reorganized by context and generic utility packages are
  removed.

No in-place compatibility alias should keep duplicate type identities alive.
Where JSON shapes are unchanged, document wire compatibility separately from
Go source compatibility.

## Testing and acceptance criteria

### Architecture

- The repository has one v2 `go.mod` for root plus framework code.
- The v2 module declares Go 1.26, and local/CI builds use a supported Go 1.26
  patch release; no v2 source must compile under Go 1.25.
- No v2 package imports a v1 root/framework path.
- `pkg/option` contains only the dependency-free generic `Option[T]` interface
  and `FunctionalOption[T]` adapter; package-specific option
  aliases and complete structs remain in their owning packages.
- `pkg/action` contains only `ActionError` and its domain-level semantic
  helpers. `Action`, `ActionFunc`, `Validator`, registrations, and phase
  execution belong exclusively to `pkg/controller/pipeline`.
- `pkg/action/*` imports only `pkg/controller/pipeline`, and only from its
  colocated `pipeline.go` adapter files; no action imports the reconciler or
  another controller package.
- `pkg/controller/pipeline` owns registration and before/main/after execution;
  `pkg/controller/reconciler` invokes it and owns object loading, finalizers,
  deletion cleanup, status persistence, events, and result interpretation.
- `pkg/controller` contains no Go source files and therefore defines no mixed
  root controller package.
- `pkg/controller/predicate` and `pkg/controller/handler` are cohesive public
  packages with no nested predicate or handler package tree. Predicate names
  and behavior may be redesigned, and redundant predicates may be removed
  after the consumer audit.
- No `pkg/controller/action/*` package tree exists.
- `pkg/kube/resources` has no imports from manifest-kit renderers,
  `pkg/controller/*`, or `pkg/action/*`.
- `api` contains no exported functions or behavioral methods other than
  generated `DeepCopy` and `DeepCopyInto` methods.
- Every public package owns a documented v2 use case; no package exists only
  to retain a v1 import path.
- Every retained exported symbol has a verified consumer or cross-context
  invariant; single-consumer implementation details are internalized.
- `pipeline.Request` has no `SkipApply`, `SkipDeploy`, or `Generated` fields;
  extensions carry optional application data, not control flow.
- `pipeline.Request` has no `Release` field, and no action receives release
  merely to coordinate deploy with GC.
- `pipeline.Request` exposes neither a controller/service-locator field nor a
  condition manager.
- `resources.Accessor` lives under `pkg/kube/resources`, not `api` or
  `pkg/controller`, and programmatic `Run` methods consume it without a
  pipeline request.
- `pipeline.Request.Resources` is a `resources.Accessor`; the request
  does not expose a mutable resource-list field or implement the accessor
  itself.
- Controller-specific actions are methods on a module controller struct and
  reach initialized renderers or other module dependencies through that
  receiver. They are registered with `pipeline.ActionFunc`; those dependencies
  are not added to `pipeline.Request`.
- Resource changes use explicit write-back and copy-on-write. `All` and `Get`
  expose borrowed, read-only objects; callers publish replacements through
  `Set`, `SetAt`, `Append`, `Filter`, or `Transform`.

### API contract

- `api.PlatformProfile` has typed common kind/version and nested distribution
  fields plus qualified annotations for distribution-specific facts.
- `Platform`, `ClusterType`, `ClusterInfo`, `AuthenticationMode`, and
  `OperatorInfo` are not part of the v2 API. Distribution-specific population
  remains outside the shared public model.
- Shared spec types never contain `api.PlatformProfile`; the profile may be
  projected only into status and status is never read back as desired-state
  input.
- A minimal fixture module CR composes `api.Status` and `api.ReleaseStatus`,
  implements `StatusAccessor` and `ReleaseStatusAccessor`, and satisfies
  `PlatformObject` without implementing any optional accessor.
- A second fixture opts into `ConditionsAccessor`, `PhaseStatusAccessor`, and
  `PlatformProfileAccessor`, with the profile stored only under status.
- Controller-gen produces compiling, correct deep copies and expected CRD
  list/map markers.
- Runtime contract validation catches nil or copy-returning required accessors
  and validates optional accessor round-tripping only when implemented.
- JSON output remains compatible for management state, conditions, observed
  generation, releases, and the optional phase field; profile JSON matches its
  new status-only contract.

### Options

- Every first-party functional-option family has an exported complete options
  struct that implements the same option interface. This includes action
  construction, per-run inputs, pipeline registration, reconciler policy,
  condition marking, and dynamic discovery.
- Every public configurable action accepts both its complete options struct and
  functional options in the same ordered list.
- No `WithX` functional option controls behavior that cannot be represented by
  a field in its related options struct.
- Each first-party option family is colocated in a descriptively prefixed
  `*_options.go` file, with matching tests in `*_options_test.go`.
- `pkg/option/option.go` is the only naming exception; no Go source file is
  named with a leading underscore.
- Options are applied left to right.
- Maps, slices, and present pointer values are cloned.
- Each constructor/configuration option family has one documented,
  authoritative set of safe defaults.
- Tests verify that `New` or the corresponding owning entry point initializes
  sensible defaults before applying any struct or functional option.
- Every option field documents its zero and nil semantics, and tests exercise
  those semantics through both the struct and functional forms.
- `CleanupTimeout` defaults to 10 minutes; an absent pointer preserves that
  default, a present zero disables the deadline, a present positive value
  overrides it, and a present negative value fails reconciler build validation.
- Public option structs prefer documented zero semantics, directed booleans,
  and mode enums when omission and zero are equivalent. Pointer fields are used
  when merging must distinguish them and are populated with Go 1.26's
  `new(value)`.
- Tests cover append, replacement, key merge, and recursive nested-option
  semantics for every field that uses them.
- Tests configure every option family once through the complete struct and once
  through equivalent functional options and assert the same effective
  configuration and behavior.
- Every public action constructor is error-free and supplies sensible defaults
  for optional behavior. Dependencies without a safe default are required
  positional arguments; optional behavior uses options. `Validate` and
  standalone `Run` still reject nil or typed-nil required interfaces before
  I/O.
- `pipeline.Action` does not require `Validate`.
- Reconciler `Build` detects `pipeline.Validator` with a type assertion and
  calls `Validate` only for actions that implement it.
- A validation error identifies the action and phase and fails `Build` before
  the controller starts.
- Missing per-run requirements fail before I/O.
- Constructed actions are safe for concurrent reconciliation when their
  configured cache supports it.
- Every action-registration method accepts both a complete `ActionOptions`
  struct (by value or pointer) and functional registration options.
- An action supplies its default name through `Name`; `WithName` overrides the
  name for one registration without mutating the action.
- Reconciler `Build` resolves all effective action names, rejects empty names,
  and rejects duplicates across before, main, after, cleanup, and
  framework-installed registrations before invoking action validation.

### Pipeline execution

- `pipeline.New` creates one immutable pipeline containing before, main, after,
  and cleanup registrations.
- `Pipeline.Validate()` is called once during reconciler `Build`; it has no
  context because it checks static names, guards, and optional action
  validators only.
- `Pipeline.Run` executes before, main, and after actions. `Pipeline.Cleanup`
  executes only cleanup actions. Neither method accepts a phase selector.
- A false guard simply skips its action without invoking `Execute`; it produces
  no outcome, condition, reason, event, or status change.
- Guard errors fail the node and follow normal action-error interpretation.
- Guards are evaluated whenever their action registration is reached on every
  reconciliation; the pipeline never caches by guard name or instance.
- A guard that needs process-lifetime singleton evaluation implements that
  behavior itself, for example with `sync.Once`, and must be concurrency-safe.
- Actions execute sequentially in registration order; no dependency graph or
  secondary ordering API is involved.
- GC placement is the controller author's responsibility. The pipeline does
  not identify or reorder GC, and `Build` does not require a special GC marker.
- `When` is opt-in for genuinely conditional main actions and is not attached
  to the normal render/deploy/GC chain by default.
- Reconciler and action defaults never inject an implicit runlevel guard.
- A global readiness check is a before action whose semantic error determines
  whether main actions start, rather than a guard copied onto every action.
- Cache hits are successful render executions and do not control GC.

### Before and after action phases

- Before, main, and after phases execute in that order; registration order is
  preserved within each phase.
- Pipeline execution carries one existing `ActionError` accumulator across all
  phases. It introduces no execution-report abstraction, per-phase result
  hierarchy, or additional error aggregation API.
- All lifecycle registrations accept the same `pipeline.Action` and
  registration options, including `WithName` and `When`.
- Each condition-producing action sets its own concrete conditions through the
  opt-in `api.ConditionsAccessor`; registration does not repeat condition
  metadata.
- Every before action whose guards pass runs and every returned error is
  aggregated. Plain and terminal before errors prevent main execution only
  after all before registrations are traversed; non-blocking and advisory
  errors allow main execution.
- Main actions are the only actions that short-circuit their own phase on a
  plain or terminal error.
- Every after action whose guards pass runs even if before or main actions
  fail, and one failing after action does not suppress the remaining after
  registrations.
- Errors from before, main, and after actions are retained in one aggregate; the
  strongest semantic outcome drives the final reconciliation result.
- When dynamic ownership is enabled, its private synchronization action is
  appended unguarded after all user after actions. It runs independently of
  earlier action outcomes and derives watches from the resource snapshot then
  available.
- Condition aggregation and phase computation remain opt-in reconciler status
  processing outside the action lists; status persistence is unconditional.
  Status processing consumes the final `ActionError` and runs even when action
  execution is blocking.
- The normal three-phase sequence never blocks deletion cleanup.
- The v2 `docs/action-error-semantics.md` document is authoritative and tests
  cover terminal/plain continuation boundaries independently for before,
  main, after, and cleanup registrations.

### Programmatic and pipeline parity

- Every shared action has tests invoking `Run` without a pipeline request.
- Every action run-options type uses the narrowest applicable existing
  controller-runtime interface: `client.Reader`, `client.Writer`, or
  `client.Client`. No project-specific Kubernetes client interfaces are
  introduced.
- Programmatic resource-producing actions work with the default
  `resources.Collection` implementation.
- Resource accessor tests cover indexed iteration and early termination,
  `SetAt` bounds checks, shallow structural copies, `Filter` retain semantics,
  ownership transfer, and atomic publication of successful `Transform`
  results.
- Accessors preserve order and duplicates without resolving object identity.
  Deploy rejects nil, incomplete, or duplicate normalized identities before
  issuing any Kubernetes write and publishes the normalized collection for
  downstream consumers.
- GC first requires `metav1.IsControlledBy(candidate, owner)`, then derives
  staleness from the desired resource identity set and
  `metadata.Policy.Matches`; it has no direct platform release, version, or
  generation inputs. Missing or mismatched controller ownership always skips
  the object.
- Omitting `WithMetadataPolicy` on either deploy or GC installs the same
  owner-derived default policy; deploy stamping and GC candidate selection
  cannot silently diverge.
- The default policy stamps owner kind, name, namespace, UID, and generation,
  and does not require release or platform information.
- Deploy publishes the policy-decorated desired snapshot through
  `resources.Accessor` before downstream resource-lifecycle actions consume it.
- A caller-owned distribution profile/release policy composes with the default
  policy; release/version values do not narrow the resulting selector because
  they would hide old resources.
- A custom `metadata.Policy` instance can be shared by deploy and GC; its
  release-aware metadata does not narrow the stable GC selector.
- Composite policy tests verify application order, selector intersection,
  all-policy matching, immutable input capture, and conflict detection.
- GC accepts `gc.TypeDiscovery` as a required positional constructor
  dependency. Standalone dynamic wiring uses uncached
  `gc.New(gc.DynamicDiscovery(discoveryClient), opts...)`; standard framework
  wiring shares a dynamic discoverer configured with
  `gc.WithEventInvalidation(mgr)`. Finite-scope controllers use
  `gc.New(gc.StaticDiscovery(gvks...), opts...)`.
- `TypeDiscoveryFunc` supports custom discovery functions. Dynamic and static
  discovery configuration is immutable after construction, and implementations
  are safe for concurrent reconciliations.
- Without `WithEventInvalidation`, dynamic discovery retains no resource-type
  snapshot and reads live discovery on every call. With it, handlers on the
  manager's shared CRD and APIService informers invalidate a lazily populated
  snapshot and the underlying client-go discovery cache; a bounded maximum age
  provides fallback refresh.
- Event-handler registration is lazy, happens on the first `Discover`, and
  returns setup or synchronization failures to that caller. Construction stays
  error-free, and the wrapper manager shares one configured discoverer rather
  than creating one cache and handler set per controller.
- The specialized Kubernetes discovery client is captured only by the dynamic
  discoverer. GC uses the ordinary controller-runtime client for REST mapping,
  listing, authorization resources, ownership checks, and deletion; neither
  `pipeline.Request` nor GC `RunOptions` exposes a discovery client.
- A final composed selector that still matches everything fails safely before
  GC lists or deletes objects; neutral selectors inside a constrained
  composition are valid.
- Each action's `Execute` method has focused request-to-run-option mapping
  tests.
- Action constructors return no error; registration accepts the minimal
  `pipeline.Action` interface, and `Build` validates the action only when it
  also implements `pipeline.Validator`.
- Running an action programmatically and through `Execute` produces the same
  resources, errors, and domain result for the same inputs.
- `pipeline.go` contains no merge, render, deploy, GC, ownership, or workload
  algorithms.
- Programmatic `Run` methods neither accept nor depend on pipeline extensions.
- Dynamic ownership has no standalone action or registrar API. It is a
  concurrency-safe, framework-managed after action installed by the reconciler
  only when enabled.
- Dynamic ownership does not depend on render/deploy success markers. It runs
  independently of pipeline outcomes, registers GVK watches from the accessor
  snapshot available at that point, and treats watch registration as additive
  controller topology.

### Status responsibilities

- `api.Status` remains a data type with generated deepcopy support only and
  contains only observed generation and conditions. `api.ReleaseStatus` and
  `api.PhaseStatus` are separate composable wire types.
- Distribution-specific bootstrap computes one `api.PlatformProfile`; retained
  copies clone annotations and remain immutable for the process lifetime.
- Functions, actions, and policies that consume the startup profile receive it
  explicitly. It is never a spec field, pipeline request field, global value,
  or per-reconcile discovery result.
- When configured with the startup profile, reconciler status processing projects a
  copy into status only for objects implementing `PlatformProfileAccessor`; it
  never reads status back as reconciliation input.
- Workload and OpenShift observation actions return observations and do not
  mutate a condition manager or persist the status subresource.
- Observation `Execute` methods use low-level condition helpers after requiring the
  instance's opt-in `api.ConditionsAccessor`.
- Low-level `MarkTrue`, `MarkFalse`, `MarkUnknown`, `Set`, `Find`, and `Remove`
  behavior remains available without constructing a manager.
- V2 does not initially implement condition `Reset`, active-condition tracking,
  expected-condition initialization, or stale-condition cleanup.
- Release discovery returns release metadata and is not grouped under workload
  or OpenShift observation actions.
- After every normal pipeline execution that reaches status processing, the
  reconciler sets observed generation to the instance generation even when the
  aggregate outcome is unsuccessful; observed means evaluated, not ready.
  If the object implements `ConditionsAccessor`, it computes framework-owned
  outcome conditions and aggregates/sorts the conditions present. If the object
  implements `PhaseStatusAccessor`, it also computes phase from the complete
  action-error aggregate.
- The reconciler then performs the final Kubernetes status write through
  `pkg/kube/resources.ApplyStatus`, consolidated with `Apply` from the
  framework resource helpers; no update-, patch-, conflict-retry, or dedicated
  status-package path remains. Neither the helper nor the reconciler classifies
  returned errors; the reconciler returns them through the normal
  controller-runtime error path and wraps only when useful context is missing.

### Renderers

- No v2 package mirrors the manifest-kit renderer, source, option, filter,
  transformer, post-renderer, metrics, or cache APIs.
- Documentation demonstrates direct Helm, Kustomize, Go-template, and composed
  engine usage from a controller-owned action.
- Any retained adapter identifies a concrete upstream gap and exposes only the
  additional ODH behavior.
- Rendering actions are implemented by controllers, not this library.
- Renderer caching is configured through manifest-kit and is not wrapped by a
  v2 action cache.
- Apply ordering is tested in deploy, not implicitly in individual renderers.

### Reconciler

- Non-generic `For` accepts a non-nil `api.PlatformObject` prototype, resolves
  its GVK, and validates that `DeepCopyObject` returns the platform-object
  capability.
- Each reconciliation uses a fresh deep copy and one direct `Get` with the
  incoming `ctrl.Request.NamespacedName`; it performs no reflection or
  singleton list.
- `Build()` has no context parameter, registers the private framework
  reconciler with the manager, and returns only `error`.
- `WithControllerName` affects only controller identity, logs, events, and
  metrics. It never changes primary-object lookup or event routing.
- A module controller struct owns renderer and module-specific dependencies;
  its methods are registered through `pipeline.ActionFunc`, while the private
  framework reconciler owns `Reconcile`.
- Existing terminal, non-blocking, advisory, joined-error, status-write, and
  finalizer behavior tests pass against the moved `action.ActionError`.
- Explicit requeue delays return a nil error as required by
  controller-runtime.
- Finalizers remain until programmatic cleanup actions complete successfully
  or the configured cleanup deadline expires when deadline enforcement is
  enabled.
- No cleanup actions means no framework finalizer. Deletion never invokes the
  normal before/main/after pipeline, deploy, label-selector GC, dynamic-watch
  synchronization, or status apply.
- Cleanup actions run in registration order under the canonical action-error
  semantics; an incomplete outcome or positive requeue request retains the
  finalizer while cleanup time remains.
- With a positive timeout, cleanup requeues cannot extend the deadline derived
  from deletion timestamp; deadline expiry emits a warning and removes the
  finalizer. With zero, cleanup has no deadline.
- Owned Kubernetes resources are deleted through owner references and native
  garbage collection, not through the cleanup-action lifecycle.
- Default requeue applies only to successful apply reconciliation.

## Recommended decisions

1. Use one `/v2` Go module and remove the framework module boundary.
2. Keep only `api` outside `pkg`; organize implementation by the `platform`,
   `kube`, `action`, and `controller` contexts, with Kubernetes resource
   operations under `pkg/kube/resources`. Keep `pkg/controller` as a
   source-free grouping directory: `pipeline` owns registrations and phase
   execution, while `reconciler` owns the controller-runtime lifecycle.
3. Use one `pkg/action/*` package per capability, with programmatic `Run` and
   thin pipeline `Execute` entry points on the same concrete action; do not
   create a parallel `pkg/controller/action/*` tree.
4. Use the dependency-free generic `pkg/option.Option[T]` and
   `FunctionalOption[T]` primitives, modeled after k8s-manifest-kit. Every
   functional-option family owns an exported complete options struct, and both
   forms compose in one ordered list with field-specific merge semantics. Use
   Go 1.26's `new(value)` where explicit pointer presence is required; do not
   add a pointer helper. Colocate each family in a descriptively prefixed
   `*_options.go` file with matching `*_options_test.go` tests.
5. Separate immutable constructor configuration from per-run inputs.
6. Do not provide a generic render action or render cache. Controllers own
   their rendering action and use manifest-kit renderer/engine caching
   directly.
7. Remove engine-specific source fields from the core pipeline request.
8. Keep execution policy out of `Request` and extensions; configure guards
   through `WithAction` options and use registration order as execution order.
9. Keep condition aggregation and status computation outside the action
   pipeline; condition-producing action `Execute` methods require the opt-in
   `api.ConditionsAccessor`, and reconciler status processing consumes the complete
   before/main/after error aggregate while honoring optional condition and
   phase capabilities.
10. Use the same action and error contracts for before, main, and after phases;
    aggregate every before and after result without short-circuiting those
    phases, short-circuit only main actions, and let each action own the concrete
    conditions it reports. Reuse the existing single `ActionError` accumulator;
    do not add an execution report or another outcome model.
11. Keep `ActionError` in `action`, preserve its classifiers, precedence,
    status, event, and scheduling behavior, and keep the intentional
    phase-scoped continuation rules in
    [`docs/action-error-semantics.md`](action-error-semantics.md). Drop
    deprecated markers in v2.
12. Keep `api` limited to contract declarations, schema markers, and generated
   `DeepCopy`/`DeepCopyInto` methods; place every behavioral helper elsewhere.
13. Carry all current production capabilities through the initial redesign,
    while reshaping, consolidating, or internalizing their implementations;
    evaluate capability removal only after the v2 design and consumers are
    concrete.
14. Leave `flakiness/` outside the v2 consolidation. Treat
    `framework/testing/` as a migration consumer that may be rewritten rather
    than as a public package whose current API must survive.
15. Give deploy and GC the same owner-derived `metadata.DefaultPolicy()` so
    programmatic use is coordinated without framework configuration, and use
    `metadata.Compose` to combine it with focused caller-owned policies. Do not
    create a second controller metadata package without a concrete shared
    implementation.
16. Make every public action constructor error-free; keep `pipeline.Action` minimal,
    expose validation as the optional `pipeline.Validator` capability, and
    have reconciler `Build` invoke it only when implemented.
17. Remove `Request.Controller` and the public dynamic-ownership action. When
    enabled, append framework-managed dynamic-watch synchronization after all
    user after actions so it shares their aggregation semantics without
    exposing controller machinery through the request.
18. Model deletion as a separate cleanup lifecycle. Register exceptional,
    ownership-inexpressible cleanup with repeatable `WithCleanupAction` and
    execute it under the canonical action-error semantics. Remove the framework
    finalizer when cleanup is complete or its enabled deadline expires. Default
    that deadline to 10 minutes, allow an explicit zero to disable it, and do
    not let cleanup requeues extend a positive deadline. Never run deploy or
    label-selector GC during deletion.
19. Keep reconciler construction conventional: use a deep-copyable primary
    prototype, load by `ctrl.Request.NamespacedName`, keep singleton lookup
    separate, use `WithControllerName` only for controller identity, and have
    the non-generic builder register the private reconciler through
    `Build() error`.
20. Keep handlers and predicates as cohesive public controller packages. Flatten
    predicate families, reuse controller-runtime where sufficient, and rework
    or remove predicates whose names or behavior do not have a verified v2
    consumer.
21. Use `pkg/action/workload` for generic workload observations and
    `pkg/action/openshift` for OpenShift-specific actions such as ImageStream
    observation. Do not use a broad generic `health` package.
22. Treat action ordering as controller-author intent. In particular, register
    GC after all desired-resource producers and transforms; do not add DAG
    scheduling, automatic reordering, or GC-specific pipeline machinery.
